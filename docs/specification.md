# PotamAId 機能仕様

> 設計の相談チャットで決めた内容を、壁打ちで見直してまとめた**modの機能面**の仕様です。開発環境（ビルド・JDK・テンプレートなど）は構築済みのため含めていません。
> 「決定」と「未決定・要調査」を分けています。未決定の項目は、勝手に決めずに作者（Bakutaku）に確認してください。

前提: NeoForge 1.21.1 / Java 21 / Mod ID `potamaid`（環境は構築済み）。Fabric を前提にした実装は採用しない。

---

## 1. 概要

- **名前**: PotamAId（川のニンフ「Potamid」と「aid（助ける）」を組み合わせ、AI をかけた造語）
- **コンセプト**: Minecraft 内のチャットから Claude Code に指示し、その場で結果を確認できる mod。
- **位置づけ**: **mod開発者（作者を含む）向けの開発ツール**。JDK と開発環境があることを前提にする。個人の趣味開発で、GitHub で公開予定。作者は初めての mod 作成。
- **最終的な目的**: メカニズム（Mekanism）やクリエイト（Create）のような**工業modを作れる**こと。それらとの**連携要素（アドオン的なもの）**も作れること。

### 基本の方式

- PotamAId は、作りたい mod（以下「対象mod」）のプロジェクトに**開発用の依存**として追加する（ModDevGradle の `localRuntime` など。配布する jar には含めない）。
- AI（Claude Code）は、**対象modのリポジトリを作業ディレクトリ**にして実行し、対象modの Java とリソースを直接編集する。
- 編集した内容は、開発環境で**ホットスワップ**（実行中のゲームのクラスを差し替える）と `/reload` によって、再起動せずに反映する。
- 編集したものがそのまま完成品になるため、スクリプトから Java への変換は行わない。

> 当初は「独自のスクリプトで即反映し、気に入ったら Java の mod に変換する（mod化）」という方式を考えていました。しかし、工業modの中心になるブロック・ブロックエンティティ・GUI などはスクリプトで即反映できる範囲の外にあること、Java への変換と挙動差の検証が難しいことから、上の方式に変更しました。これに伴い、スクリプトランタイム、スクリプト API、mod化パイプライン、汎用ブロック／アイテム（仮置き用の枠）は不要になりました。

## 2. 全体構成

### コアの機能

1. ゲーム内チャット UI
2. AI 連携（Claude Code をヘッドレスで実行する。CLI を子プロセスとして呼ぶ）
3. ホットリロード（コンパイル、クラスの差し替え、データの再読み込み、再起動が必要かの判定）
4. 承認と undo
5. ゲーム内 MCP サーバー（[6章](#6-ゲーム内の情報を-ai-に渡す)）

テクスチャ作成などは「拡張」として追加する（[7章](#7-拡張システム)）。

### 設計ルール

- コアの処理（AI 連携、承認と undo、クラスの差し替え、MCP ツールの中身）は、ローダーのクラスに依存させない。
- NeoForge に依存する部分（登録、イベントの購読、ネットワーク、設定）は薄い層にまとめる。
- Mixin は今は使わない。公式のイベント・登録の仕組みで足りる範囲で作り、必要になってから追加する。
- AI の実行は**論理サーバー側**に置き、チャット UI は**クライアント側**に置いて、間はパケットで通信する。シングルプレイでは同じ JVM の中だが、この形にしておけば、後からマルチプレイに対応するときに構成を変えずに済む（[8章](#8-安全性と利用範囲)）。
- クラスの差し替えは、PotamAId が入っている各 JVM がそれぞれ行う。
- AI の呼び出し部分はインターフェースで分ける。最初は Claude Code だけに対応し、後から Codex を追加する。

## 3. 開発フロー（ユーザー体験）

1. 対象modの開発環境で、PotamAId を入れてゲームを起動する。開発用のワールドに自動でログインする。
2. ゲーム内のチャットで AI に指示する。必要に応じて、見ているブロックや手持ちのアイテムを添付する（`@looking` など）。
3. AI が対象modのコードとリソースを編集する。PotamAId がコンパイルし、実行中のゲームに反映する。
4. 結果をゲーム内で試し、「採用」か「戻す」を選ぶ。ゲーム内で変更の要約と差分を確認できる。
5. 再起動が必要な変更（新しいブロックの登録など）の場合は、チャットで知らせ、再起動する。
6. 採用した変更は、通常の開発と同じようにコミットする。

## 4. 反映と再起動

### 再起動なしで反映できるもの

| 変更の種類 | 反映の方法 |
|---|---|
| メソッドの中身の変更 | クラスの差し替え（通常の JDK でも可能） |
| メソッド・フィールドの追加など、クラスの構造の変更 | クラスの差し替え（JBR の場合） |
| レシピ・ルートテーブル・タグなどのデータ | `/reload` |
| テクスチャ・モデル・翻訳などのアセット | リソースの再読み込み（F3+T 相当） |

### 再起動が必要なもの

- ブロック・アイテムなどの**新しい登録**（起動時に登録されて固定されるため）
- 新しいイベントリスナーの登録など、起動時にしか読み込まれない処理の変更
- クラスの差し替えに失敗した変更（通常の JDK での構造の変更など）

### JBR（JetBrains Runtime）

- JBR は**推奨とし、必須にはしない**。
- JBR のときは `-XX:+AllowEnhancedClassRedefinition` で、クラスの構造の変更も差し替える。
- 通常の JDK のときは、差し替えられない変更を再起動で対応する。

### 「再起動が必要」の判定

次の2つを組み合わせて判定する。

- クラスの差し替えを試した結果（失敗したら再起動が必要）
- AI による報告（構造化した出力で報告させる）。差し替えに成功しても、起動し直さないと反映されない変更（新しい登録など）を拾うため。

再起動が必要なときは、チャットで知らせ、再起動のボタンを出す。

### 再起動の待ち時間を減らす

- 開発用ワールドへの自動ログインは、`--quickPlaySingleplayer` などの起動引数で行う。
- 自動再起動の方式は未決定（技術検証で決める）。候補は次の2つ。
  - **ランチャー方式**: PotamAId が専用の起動タスクを用意する。ゲームが「再起動してほしい」という終了コードで終了したら、ビルドし直して起動し直す。
  - **自己再起動方式**: ゲームが自分の起動コマンドを読み取って新しいプロセスを起動し、自分は終了する。
- 工業modの開発では登録の追加が多いため、自動再起動の優先度は高めにする。

## 5. 承認と undo

### 反映のタイミング

Config で切り替えられるようにする。

| モード | 流れ |
|---|---|
| **先に反映（初期値）** | AI の編集 → コンパイル → 差し替え → 試す → 「採用」か「戻す」を選ぶ |
| 承認してから反映 | AI の編集 → ゲーム内で差分を確認 → 承認 → コンパイル → 差し替え |

- どちらのモードでも、ゲーム内で変更の要約と差分を確認できるようにする。

### AI に許可する操作

- Claude Code はヘッドレスで実行し、`--allowedTools` で許可するツールを絞る（ファイルの読み書き、検索、`gradlew compileJava` など）。
- 許可していないツールが必要になったときは、ゲーム内で確認を求める。

### undo

- 指示を実行する前に、作業ツリーの状態を Git に記録する（`git stash create` で作ったコミットを `refs/potamaid/...` に保存する）。ユーザーのブランチにはコミットを作らない。
- 「戻す」を選んだら、記録した状態にファイルを戻し、再コンパイルして差し替える。
- ワールドの変更の undo は難しめで、方式は未決定（開発用のワールドなので優先度は低め）。

## 6. ゲーム内の情報を AI に渡す

ゲーム内の情報を AI に渡す方法は2つある。

- **添付機能**: 指示に最初から情報を添える（VSCode で選択範囲を AI に渡すのと同じ発想）。
- **ゲーム内 MCP サーバー**: AI が必要なときに、自分でゲームの情報を取得し、操作する。

### 添付機能

| 添付する内容 | 取得方法 | 難易度 | 実装時期 |
|---|---|---|---|
| 見ているブロック／エンティティ | 視線のレイキャストで種類・座標・NBT を取得 | 低 | ステップ2 |
| 手持ちのアイテム | 手持ちアイテムの情報を取得 | 低 | ステップ2 |
| プレイヤーの位置・向き・周囲のエンティティ | プレイヤー情報とワールドから取得 | 低 | ステップ2 |
| 直前のログやエラー | `latest.log` を読む | 低 | ステップ2 |
| 範囲選択した領域 | `/pos1` `/pos2` などで2点指定（杖でも可） | 中 | ステップ6 |
| スクリーンショット | 画像として渡す（対応モデル限定） | 中 | ステップ4以降 |

- 参照記法の案: `@looking`（見ているもの）、`@held`（手持ち）、`@selection`（選択範囲）。
- 大きい範囲はサイズ上限を決め、超えたら要約するか、構造物ファイル（structure NBT）に書き出してパスだけ渡す。
- AI には構造化したテキスト（JSON など）として添付する。

### ゲーム内 MCP サーバー

- PotamAId が実行中のゲームの中で MCP サーバー（localhost）を立て、Claude Code に `--mcp-config` で接続させる。**コアの機能**とする。
- 目的: AI が、書いたコードをゲームの中で確かめるところまで、自分で進められるようにする。
- ツールの例:
  - 見ているブロック・手持ちのアイテムの取得
  - ログ・エラーの取得
  - コマンドの実行（`/reload`、`/give`、GameTest など）
  - スクリーンショット
- ツールは「読み取り専用」と「変更あり」に分ける。変更ありのツールは、反映モードの設定（[5章](#5-承認と-undo)）に従う。

## 7. 拡張システム

### 拡張で足せるもの

1. **MCP ツール**（例: テクスチャ作成の拡張なら、PNG を生成して assets に書き出すツール）
2. **ゲーム内 UI のタブ**（例: 生成したテクスチャのプレビュー）
3. **AI 向けの知識**（Claude Code のスキルや指示の断片。例: NeoForge 1.21.1 の API の使い方。AI が古いバージョンの API と混同するのを防ぐ）

### 拡張の単位

- 1・2 を含むものは、**PotamAId の API を使う別mod**にする（これも開発用の依存として入れる）。
- 3 だけのものは、**ファイル（スキルなど）として配布**する。

### 方針

- 最初の拡張は**テクスチャ作成**。生成した画像は通常のリソースとして書き出す。
- **早すぎる分割は避ける**。まず1つ目の拡張を実際に作り、必要になった API をコアに戻す。
- 拡張に権限を宣言させる仕組みは設けない（Java の mod は実際には制限できないため）。安全性は、MCP ツールの「読み取り専用／変更あり」の区別と、反映モードの設定で確保する。

## 8. 安全性と利用範囲

- チャットから AI を動かせることは、事実上「任意のコードを実行できる」のと同じなので、指示を出せる人を限定する。
- 最初は**シングルプレイ（統合サーバー）で、ローカルのプレイヤーだけ**が使えるようにする。
- AI が編集するのは対象modのリポジトリの中だけとし、変更は Git で戻せる状態にする（[5章](#5-承認と-undo)）。

### マルチプレイ（後回し）

将来、次の使い方に対応する。

- **専用サーバーでの動作確認**: 1人で、同じ PC で `runServer` と `runClient` を動かす。AI は1つのリポジトリを編集し、サーバーとクライアントの両方の JVM に差し替える。
- **テストプレイを見ながらの調整**: サーバー側の PC で AI を動かし、サーバー側のロジックを差し替える。クライアント側のコードの変更は、相手に再接続や再起動をしてもらう。

複数人での共同開発（各クライアントへのコードの配布）は対象にしない。

マルチプレイでは、AI に指示できるプレイヤーを、OP 権限と Config の許可リストで限定する。初期状態では無効にする。

## 9. 工業mod・連携

- 工業modそのものや、Create・Mekanism などとの連携は、**PotamAId を使って別のリポジトリで作る**。PotamAId を実際に使って試す場にもなる。
- PotamAId 側は、その開発を**知識ファイル**（[7章](#7-拡張システム)の3）で支援する。
- 連携は、各modが公開している API やイベントを使う。連携ごとに、対象modの対応バージョンと API を調べてから実装する。
- NeoForge 1.21.1 には、エネルギー・流体・アイテムの受け渡しの仕組み（Capabilities）がある。工業mod側の設計時に調べて使う（詳細は要調査）。

## 10. 実装の順序

0. **技術検証**: NeoForge の上でのクラス差し替え（JBR と通常の JDK）、Java エージェントの組み込み方、自動再起動の方式、Claude Code のヘッドレス呼び出し。ここで基本の方式が成り立つかを確かめる。
1. チャット → Claude Code → 結果の表示（まず動かす）。最初から「論理サーバーで実行し、パケットで通信する」構成にする。あわせて、開発用ワールドへの自動ログインを用意する。
2. ホットスワップでの反映、データの `/reload`、再起動が必要かの判定。「見ているブロック」「手持ちのアイテム」などの添付も入れる。
3. ゲーム内 MCP サーバー（読み取り専用のツールから）。
4. undo、反映モードの切り替え、差分の表示。MCP の「変更あり」のツール（コマンドの実行、スクリーンショット）。
5. 自動再起動。
6. 拡張システム（テクスチャ作成から）。範囲選択の添付。
7. マルチプレイ対応、Codex への対応。
8. PotamAId を使って工業modを作る。Create・Mekanism などとの連携。
