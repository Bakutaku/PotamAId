# PotamAId 機能仕様

> 設計の相談チャットで決めた内容を、壁打ちで見直してまとめた**modの機能面**の仕様です。開発環境（ビルド・JDK・テンプレートなど）は構築済みのため含めていません。
> 「決定」と「未決定・要調査」を分けています。未決定の項目は、勝手に決めずに作者（Bakutaku）に確認してください。
> 2026-10-18 に、AI の実行を Mod の外の常駐プロセス（PotamAId Bridge）に移し、Claude Code・Codex が提供する SDK を使う方針に改めました（[経緯](#方針変更の経緯)）。
> 2026-10-25 に、AI とのやり取りの単位を「チャット」から「目標・タスク・相談」に改め、Bridge のアプリの画面でも指示と承認を行う方針にしました（[3章](#目標タスク相談)・[5章](#アプリの画面)）。同日に、確認をタスクごとから目標の単位に改め、調査タスクの並行実行と通知を加えました（[3章](#目標の進め方)）。さらに同日、目標ごとの worktree で編集タスクを並行して実行する方式と、タスクごとのモデルの選び方を加えました（[3章](#worktree-での並行実行)・[6章](#実行の設定とモデルの選び方)）。2026-11-01 に、ローカル LLM への対応を取りやめました（[6章](#実行の設定とモデルの選び方)）。この文書は実装済みの機能だけでなく、今後の実装方針も含みます。

前提: NeoForge 1.21.1 / Java 21 / Mod ID `potamaid`（環境は構築済み）。Fabric を前提にした実装は採用しない。

---

## 1. 概要

- **名前**: PotamAId（川のニンフ「Potamid」と「aid（助ける）」を組み合わせ、AI をかけた造語）
- **コンセプト**: Minecraft の mod 開発を支援する AI 連携 mod。ゲーム内から Claude Code・Codex に指示でき、既存の Claude Code・Codex からはゲームの情報を取得できる。
- **位置づけ**: **mod開発者（作者を含む）向けの開発ツール**。JDK と開発環境があることを前提にする。個人の趣味開発で、GitHub で公開予定。作者は初めての mod 作成。
- **最終的な目的**: メカニズム（Mekanism）やクリエイト（Create）のような**工業modを作れる**こと。それらとの**連携要素（アドオン的なもの）**も作れること。

### 2つの利用形態

| 利用形態 | 指示・進捗の確認を行う場所 | PotamAId の役割 |
|---|---|---|
| **① ゲーム内から AI を使う** | Minecraft 内の PotamAId の UI | 指示の受け付け、ゲーム情報の添付、進捗の表示、会話のセッション管理。AI の実行は Bridge が行う |
| **② 既存の Claude Code・Codex から使う** | 既存のアプリ（CLI・IDE の拡張機能・デスクトップアプリなど） | MCP サーバーとして、ゲームの情報の取得とゲーム内の操作（コマンドの実行など）を提供するだけ。既存アプリの操作機能は置き換えない |

- ②は Bridge を起動しなくても使える。
- ソースコードの差分の確認や Git の操作は、VS Code などの既存の開発ツールで行うことを基本とし、ゲーム内での実装は必須にしない。

### 基本の方式

- PotamAId は、作りたい mod（以下「対象mod」）のプロジェクトに**開発用の依存**として追加する（ModDevGradle の `localRuntime` など。配布する jar には含めない）。
- AI（Claude Code・Codex）は、**対象modのリポジトリを作業ディレクトリ**にして実行し、対象modの Java とリソースを直接編集する。①では Bridge が、②では利用者が起動した既存のアプリが AI を実行する。
- **AI の実行は Minecraft のプロセスから切り離す。** mod 開発中はゲームを頻繁に再起動するため、ゲームの終了で AI の作業を止めないようにする（[8章](#8-minecraft-の再起動への対応)）。
- 編集した内容をゲームに反映する方法（ホットスワップ・`/reload`・再起動）は [9章](#9-コードの反映とゲームの再起動)。クラスの差し替えの手段は未決定。
- 編集したものがそのまま完成品になるため、スクリプトから Java への変換は行わない。

> 当初は「独自のスクリプトで即反映し、気に入ったら Java の mod に変換する（mod化）」という方式を考えていました。しかし、工業modの中心になるブロック・ブロックエンティティ・GUI などはスクリプトで即反映できる範囲の外にあること、Java への変換と挙動差の検証が難しいことから、上の方式に変更しました。これに伴い、スクリプトランタイム、スクリプト API、mod化パイプライン、汎用ブロック／アイテム（仮置き用の枠）は不要になりました。

### 方針変更の経緯

> 2026-10-18 までの仕様では、Claude Code の CLI を論理サーバーの子プロセスとして実行し、会話の管理・承認・undo・差分の表示までを Mod の中で行う方式でした。しかし、mod 開発中はゲームを頻繁に再起動するため、ゲームのプロセスで AI を動かすと作業が途中で止まってしまいます。また、利用者は複数のモニターを使い、VS Code などで差分を確認する開発者が多いと考えられます。
> そこで、AI の実行と会話の管理をゲームの外の **PotamAId Bridge** に移し、Mod はゲーム内の UI・ゲーム情報の提供・MCP サーバーに専念する方式に変更しました。あわせて、既存の Claude Code・Codex から MCP でゲームの情報を使う利用形態（②）を加えました。

## 2. 全体構成

```text
① ゲーム内から使う
  ゲーム内 UI（Mod） ⇄ PotamAId Bridge ⇄ Codex app-server / Claude Agent SDK
                                                │ MCP でゲーム情報を取得
  Mod の MCP サーバー ◀─────────────────────────┘

② 既存のアプリから使う
  既存の Claude Code / Codex ── MCP ──▶ Mod の MCP サーバー
```

### 構成要素と責務

| 構成要素 | 動作する場所 | 主な責務 |
|---|---|---|
| **Minecraft Mod** | ゲームのプロセス | ゲーム内 UI の提供、ゲーム情報の取得、スクリーンショットの取得、MCP サーバーの提供（論理サーバー側）、Bridge との通信（クライアント側） |
| **MCP サーバー** | Mod のプロセスの中（論理サーバー側） | ゲーム情報の取得とゲーム内の操作を MCP のツールとして提供する。クライアントにしかない情報はパケットでクライアントから取得する（[4章](#4-ゲームの情報を-ai-に渡す)） |
| **PotamAId Bridge** | Minecraft とは独立したローカルプロセス | AI の実行管理、目標・タスク・相談と AI のセッションの管理、進捗の取得と Mod への通知、タスクの実行順の管理、キャンセル、Mod の再接続の管理、承認が必要な操作の管理、アプリの画面の提供（[5章](#5-potamaid-bridge)） |

### 設計ルール

- AI の実行と会話の管理は Bridge に置き、Mod には置かない。
- ゲーム情報の取得処理は共通化し、①②のどちらの MCP 接続からも同じものを使う。添付機能（[4章](#4-ゲームの情報を-ai-に渡す)）でも使えるようにする。
- Bridge の中では、AI プロバイダーごとの実装を共通のインターフェースで抽象化する（[6章](#6-ai-プロバイダー)）。
- コアの処理（ゲーム情報の取得と MCP ツールの中身、クラスの差し替え）は、ローダーのクラスに依存させない。
- NeoForge に依存する部分（登録、イベントの購読、ネットワーク、設定）は薄い層にまとめる。
- Mixin は今は使わない。公式のイベント・登録の仕組みで足りる範囲で作り、必要になってから追加する。
- Minecraft のメインスレッド（サーバー・クライアント）や描画スレッドで実行する必要がある処理は、そのスレッドにディスパッチする。MCP サーバーや Bridge との通信のスレッドから、ゲームの状態を直接読み書きしない。
- クライアント専用のコード（描画・画面・スクリーンショット）は、`Dist.CLIENT` 限定のクラスにだけ置く。
- MCP サーバーは論理サーバー側に置き、クライアントにしかない情報はパケットでクライアントから取得する（[4章](#4-ゲームの情報を-ai-に渡す)）。
- Bridge との通信は**クライアント側だけ**に置く。ゲーム内 UI を持つクライアントが、同じ PC で動く Bridge に直接接続する（[5章](#5-potamaid-bridge)）。論理サーバーは Bridge と通信しない。

## 3. 利用形態とユーザー体験

### ① ゲーム内から AI を使う

1. Bridge のアプリを起動しておく（[5章](#起動と配布)）。PotamAId を入れてゲームを起動し、シングルプレイのワールドを開く。必要に応じて、コマンドで開発用ディメンションへ移動する。
2. ゲーム内のチャットや専用の UI から AI に指示する（目標を立てる、相談する、タスクに追加で指示する）。必要に応じて、見ているブロック・手持ちのアイテム・プレイヤーの座標・スクリーンショットなどを添付する。Bridge のアプリの画面からも指示できる。
3. Mod が指示と添付を Bridge に送り、Bridge が AI を実行する。目標は、AI が作った計画をユーザーが承認してから、タスクごとに実行する（[目標・タスク・相談](#目標タスク相談)）。AI は対象modのコードとリソースを編集し、必要に応じて MCP でゲームの情報を取得する。
4. AI の実行状態と作業の進捗を、ゲーム内と Bridge のアプリの画面に表示する。ゲームを再起動しても、Bridge に再接続して続きを確認できる。
5. 変更の差分の確認とコミットは、VS Code などの既存の開発ツールで行う。
6. 変更の反映（ホットスワップ・`/reload`・再起動）は [9章](#9-コードの反映とゲームの再起動) で扱う。

| ゲーム内の機能 | 扱い |
|---|---|
| ゲーム内のチャット・専用 UI からの指示 | 提供する。最初はチャット（コマンド）で提供し、見やすい専用の画面は後から用意する（形は未決定） |
| スクリーンショットの取得と添付 | 提供する |
| スクリーンショットへの書き込み・範囲の指定 | 将来の機能 |
| プレイヤーの座標や対象のブロックなどの共有 | 提供する（[4章](#4-ゲームの情報を-ai-に渡す)） |
| AI の実行状態・作業の進捗の表示 | 提供する |
| 目標・タスク・相談の管理 | 提供する（実体は Bridge が管理する） |
| ゲームの再起動後のセッションへの復帰 | 提供する（[8章](#8-minecraft-の再起動への対応)） |
| 差分の確認・Git の操作 | 必須にしない（既存の開発ツールを使う） |

### ② 既存の Claude Code・Codex から使う

- 既存の Claude Code・Codex に、PotamAId の MCP サーバーを接続する。接続の設定方法はそれぞれの公式の手順に従い、利用手順として文書にまとめる。
- AI への指示・進捗の確認・承認は、既存のアプリ側で行う。PotamAId はゲームの情報と操作の提供に徹し、既存アプリの操作機能を置き換えない。
- Bridge を起動しなくても使える。
- 論理サーバーが動いていない間（シングルプレイでは、ワールドを開いていない間）は、MCP サーバーも使えない（[4章](#4-ゲームの情報を-ai-に渡す)・[8章](#8-minecraft-の再起動への対応)）。

### 開発用ディメンション

- 開発用の空間は、同じセーブデータ内の専用ディメンション `potamaid:development` とする。
- コマンドで移動・帰還する。ワールドに入っただけで自動移動はしない。
- 初期構成は、**中央の拠点島と汎用の実験島3つ**。島の下面は、厚みを抑えた丸い形状にする。
- 中央の拠点島には、到着広場、屋根付きの管理棟、実験島ごとの色分けした案内所、照明・外周の手すりを用意する。管理棟には作業台・石切台・鍛冶台・金床と、チャット・帰還コマンドの案内板を置く。
- 実験島は、建物や実験設備を配置できる草地にする。実験島ごとの用途と建物は後から追加する。
- `/potamaid dev` で拠点島、`/potamaid dev <島名>` で指定した島へ移動する。島名は `hub`、`experiment_1`、`experiment_2`、`experiment_3`。
- `/potamaid back` で、入る前のディメンション・座標・向きへ戻る。帰還位置はプレイヤーに保存し、再ログイン後も使えるようにする。島間の移動で元の帰還位置を上書きしない。
- 移動先に立てる空間と足場がなければ近くを探し、見つからなければ移動を中止する。元のディメンションが存在しない場合や帰還位置が記録されていない場合は、オーバーワールドのスポーン地点付近へ戻す。
- 浮島の地形は新規チャンク生成時に作り、建築内容は通常のワールドと同じように保存する。
- 初期地形を更新しても、生成済みの島を自動では上書きしない。地形を作り直す場合は、ワールドを終了して開発用ディメンションだけをバックアップへ退避し、次回起動時に再生成する。
- シングルプレイのローカルプレイヤーだけが移動コマンドを使えるようにする。
- 今後、ディメンション間・島間の移動やチャットを支援するアイテムツールを追加する。具体的な種類や操作方法は別途決める。
- 管理棟の奥の壁に、目標・タスクの作業状態を表示する**作業ボード**を置く（下の「目標・タスク・相談」を参照）。

### 目標・タスク・相談

AI とのやり取りは、ファイルを編集する「目標」と、編集しない「相談」に分けて扱う。

| 種類 | 内容 | AI の権限 |
|---|---|---|
| **目標** | 「○○を実装したい」という依頼。実装までに必要な作業を**タスク**に分けて、順に実行する | 編集タスクではファイルを編集できる。計画の作成と調査タスクは読み取り専用 |
| **相談** | 実装を伴わない質問・調べもの。普通のチャットと同じく、会話履歴を引き継いでやり取りする | 読み取り専用 |

- 目標・タスク・相談と AI のセッションは **Bridge が管理する**。会話の本文は、各プロバイダーの通常のセッション保存先に残す想定。Bridge は、目標・タスク・相談とセッション ID などを SQLite に保存する（[5章](#セッションの永続化)）。どれも対象modごとに分けて管理する。
- 目標・タスク・相談の情報は Bridge が対象modごとに持つため、ワールドのセーブには保存しない。同じ対象modなら、どのワールドを開いても同じものを使える。

#### 目標の進め方

1. ユーザーが目標を書く（例: 「鉄鉱石を2倍にする粉砕機を追加したい」）。
2. AI が読み取り専用でコードを調べ、**計画**（タスクの一覧と、タスク同士の依存関係）を作る。タスクは、ファイルを編集する**編集タスク**と、読み取り専用で調べるだけの**調査タスク**に分ける。
3. ユーザーが計画を確認し、タスクの編集・削除・追加（編集と調査の切り替えを含む）をしてから**承認**する。指示を足して計画を作り直させることもできる。
4. Bridge が、目標の worktree を作り、依存関係の順にタスクを実行する（[worktree での並行実行](#worktree-での並行実行)）。AI が終えたタスクは、そのまま「完了」にして次のタスクに進む。
5. 目標のタスクがすべて完了したら、目標の変更をゲームを起動するディレクトリに反映し、目標を「確認待ち」にして通知する（[通知](#通知)）。ほかの目標が確認中なら、反映を待つ。ユーザーはゲーム内や VS Code で目標の全体を確かめ、問題がなければ目標を「完了」にする。直してほしい点があれば、目標かタスクに指示する。

- タスクごとの確認はしない（2026-10-25 決定）。機能の全体ができるまで動作を確かめられないことが多く、タスクごとに確認を待つと時間がかかりすぎるため。ゲームの再起動が必要な変更も、目標の確認待ちのときにまとめて知らせる。
- **タスクごとに別の AI のセッションを使う。** タスクを始めるときに、目標・計画の方針・計画のタスクの一覧（番号・題名・種類・依存・状態）と、依存先のタスクの結果を指示に添える。1つのセッションで続けると、タスクが増えるほど会話が長くなるため。
- ほかのタスクの説明や結果は指示に含めず、AI が必要なときに [Bridge の MCP ツール](#bridge-の-mcp-ツール)で調べる（2026-10-25 決定）。指示が長くなりすぎないようにするため。依存先のタスクの結果は、読まずに進めると困るため、これまでどおり指示に添える。
- AI の履歴で内容を見分けやすいように、指示の先頭には、計画の作成・見直しでは目標名、タスクの実行ではタスク名と目標名・番号・種類を書く。
- **編集タスクは、目標ごとの worktree で実行し、別の目標の編集タスクと並行できる**（2026-10-25 決定）。1つの目標の編集タスクは、その worktree で1件ずつ実行する。詳しくは [worktree での並行実行](#worktree-での並行実行)。
- 計画の作成・調査タスク・相談は読み取り専用なので、編集中のタスクと**並行して実行できる**（調査タスクは 2026-10-25 決定）。並行して実行する数の上限は、**対象modごとに Bridge の設定で持つ**。超えた分は順番待ちに入れて、空いた順に実行する。計画の作成と相談は、ユーザーが応答を待っているため、調査タスクより先に枠に入れる。
- 調査タスクの結果は、そのタスクに依存するタスクの指示に添えて渡す。
- 依存するタスクがあるタスクは、依存先が「完了」になってから実行する。失敗したタスクに依存するタスクは止まるが、依存しないタスクは続けて実行する。
- **対象modに「確認中」の目標がある間は、他の目標の変更をゲームを起動するディレクトリに反映しない。** 確かめる変更に、別の変更を混ぜないため。他の目標の編集タスクは、それぞれの worktree で続けて実行する。「確認中」は、目標が確認待ちになってから完了にするまでの間で、修正を実行している間も含む。
- 中止したタスクは「未着手」に戻し、**ユーザーが再開するまで自動では実行しない**。停止中かどうかはタスクの状態とは別に保存し、Bridge の再起動後も維持する。「再開」を選ぶか、そのタスクに追加の指示を送ると停止を解除し、依存関係と実行枠に従って実行する。セッションは次の実行で新しく作る。「すべての実行を中止」では、実行中のものに加え、待機中のタスクと追加指示の自動実行も停止する。中止しても、それまでのファイルやワールドの変更が自動で戻るとは限らない（[10章](#差分と-undo)）。
- 相談の内容から目標を作れるようにする案がある。

#### worktree での並行実行

確認を目標の単位にしたため、タスクの実行中にゲームから確かめる必要がなくなった。そこで、編集タスクを目標ごとの git worktree で実行し、別の目標と並行できるようにする（2026-10-25 決定）。

- **worktree は目標ごとに作り、タスクごとには作らない。** mod 開発では、登録のクラス・翻訳のファイル・データ生成のプロバイダーなどを多くのタスクが触るため、タスクごとに分けると反映のたびに競合しやすい。また、依存先のタスクの変更が同じ worktree にあるほうが扱いやすい。
- 計画を承認したら、Bridge が目標のブランチ（`potamaid/goal-<目標の ID の先頭8文字>`）と worktree を作る。分岐元は、ゲームを起動するディレクトリでいま使っているブランチとする。対象modのフォルダーがリポジトリの中のフォルダー（`mod/` など）なら、worktree でも同じ場所を AI の作業ディレクトリにする。
- **worktree は Bridge のユーザーデータのディレクトリ（`<ユーザーデータ>/worktrees/<対象mod>/<目標>`）に置く**（2026-10-25 決定）。リポジトリの周りを散らかさず、Gradle や VS Code の検索にも入らないため。
- **対象modが git のリポジトリでない、コミットが1つもない、ブランチにいない（detached HEAD）ときは、計画を承認できない**（2026-10-25 決定）。理由を出して、git の準備を案内する。
- タスクが終わるたびに、**Bridge が**目標のブランチにコミットする。AI にはコミットさせない（Codex のサンドボックスでは、worktree の `.git` が作業ディレクトリの外にあるため）。タスクごとのコミットは、[10章](#差分と-undo)の undo にも使える。
  - コミットのメッセージは `potamaid: #<番号> <題名>`。失敗・中止したタスクの途中までの変更も「（失敗・途中まで）」などを付けてコミットし、同じ目標の次のタスクのコミットに混ざらないようにする。
  - 利用者の commit フックは、利用者のコミットのためのものなので実行しない（`--no-verify`）。git に名前とメールアドレスの設定がなければ、Bridge の名前（PotamAId Bridge）でコミットする。
  - 完了したタスクの変更をコミットできなければ、そのタスクを失敗にする。
- 同時に実行する編集タスクの上限は、対象modごとに Bridge の設定で持つ。初期値は1（並行しない）とする。並行すると、プランの利用枠も速く使う。
- 目標のタスクがすべて完了したら、分岐元のブランチの新しい変更を目標のブランチに取り込む。競合したら、競合を解く編集タスク（重さは `heavy`）を目標に追加し、worktree の中で AI に実行させる。そのタスクが終わったら、Bridge が取り込みのコミットを作り、もう一度反映を試みる。
- 対象modに確認中の目標がなければ、目標の変更をゲームを起動するディレクトリに反映し、目標を確認中にする。確認中の目標があれば「反映待ち」にし、確認が終わった（目標を完了にした）ときに、反映待ちの最も古い目標から反映する。
- 反映は、**コミットしない変更として置く**（`git merge --squash` 相当。2026-10-25 決定）。VS Code などで差分を確かめてから利用者がコミットする、いまの運用に合わせるため。変更はステージした状態で置く。
- **ゲームを起動するディレクトリに、コミットしていない変更（git 管理下のファイル）があるときは、反映を止めて「反映待ち」のまま知らせる**（2026-10-25 決定）。利用者の変更と目標の変更が混ざらないようにするため。利用者がコミット（または退避）してから「反映する」を押すと、もう一度試す。前の目標を完了にしたが、その変更をまだコミットしていない場合も同じ。
  - ゲームを起動するディレクトリのブランチが分岐元と違うとき、反映に失敗したとき（git 管理外のファイルを上書きしてしまうときなど）も、理由を出して反映待ちにする。
- **反映したあとの確認中の修正（目標・タスクへの指示）は、ゲームを起動するディレクトリで実行する**（2026-10-25 決定）。ゲームで確かめながら直せるようにするため。修正はコミットしない変更に重なり、Bridge はコミットしない。反映待ちの目標への指示は、worktree で実行してから反映し直す。
- **完了にした目標の worktree は消し、ブランチは残す**（2026-10-25 決定）。タスクごとのコミットを undo に使えるようにするため。ブランチは利用者が git で消す。
- worktree を持たない以前の目標（この方式の前に承認したもの）は、ゲームを起動するディレクトリで実行し、反映はしない。
- worktree の中の AI は、ゲームの MCP で自分の変更を確かめられない（つながるゲームは、ゲームを起動するディレクトリのコードで動いているため）。worktree の中で確かめられるのは、コンパイルや、worktree から起動する GameTest などに限られる。
- Gradle の出力（`build/`）は worktree ごとにできるため、ディスクを使い、初回のビルドに時間がかかる。`mod/run/` など git 管理外のファイルは worktree にない。

#### 確認と修正の指示

- 目標の確認で直してほしい点が見つかったら、**目標**と**タスク**のどちらにも指示できる（2026-10-25 決定）。
  - **目標への指示**: 修正の編集タスクを目標に1件追加して実行する。修正のタスクは目標のほかのタスクすべてに依存させ、それまでのタスクの結果を添えて新しいセッションで実行する。原因のタスクが分からなくても指示できる。
  - **タスクへの指示**: そのタスクのセッションの続きで実行する。そのタスクで何をしたかを AI が覚えているため、直す範囲が狭く済む。
- 目標への指示は、確認待ち・完了の目標で受け付ける。タスクへの指示は、計画を承認した目標であれば受け付ける。実行中のタスクへの指示は、いまのターンが終わってから渡す。
- 完了にした目標に指示したときは、目標を確認中に戻す。修正がすべて終わったら、もう一度確認待ちとして通知する。
- 目標を完了にできるのは、目標のタスクがすべて完了しているときだけとする。

#### 計画の形式

- 計画は、AI の最後の発言を JSON Schema で指定した形（構造化出力。Codex は `turn/start` の `outputSchema`）にさせる。形は `{ goalTitle, summary, tasks: [{ key, title, description, kind, weight, dependsOn: [key] }] }` とする。`kind` は編集タスクが `edit`、調査タスクが `investigate`。`weight` はタスクの重さで、実行に使うモデルを決めるのに使う（[6章](#実行の設定とモデルの選び方)）。
- Bridge は、識別子の重複、存在しないタスクへの依存、自分自身への依存、循環を検証してから保存する。依存先が先に来るように並べ替えて番号を振る。計画を承認するときにも、編集後の依存関係を同じく検証する。
- 指示を足して作り直すときは、計画を作ったセッションの続きで、いまの計画（ユーザーの編集を含む）を添えて作り直させる。
- タスクの結果も構造化出力で報告させる。編集タスクは `{ summary, needsGameRestart }`、調査タスクは `{ summary }` とする。`needsGameRestart` は、再起動が必要かの AI による報告（[9章](#再起動が必要の判定)）に使う。

#### 目標の状態

| 状態 | 内容 |
|---|---|
| 計画中 | AI が計画を作っている（順番待ちを含む） |
| 計画の確認待ち | 計画ができ、ユーザーの確認と承認を待っている |
| 計画の失敗 | 計画の作成に失敗した。やり直せる |
| 進行中 | 計画を承認し、タスクを実行している。反映の前の競合の解消を含む |
| 反映待ち | タスクがすべて完了し、ゲームを起動するディレクトリへの反映を待っている（ほかの目標の確認中、コミットしていない変更がある、反映に失敗したなど。理由を表示し、「反映する」でやり直せる） |
| 確認中 | タスクがすべて完了し、ユーザーが目標を確かめている。修正を実行している間は「修正中」、修正がなければ「確認待ち」と表示する |
| 完了 | ユーザーが目標の確認を済ませた |

#### タスクの状態

| 状態 | 内容 |
|---|---|
| 未着手 | まだ実行していない。依存先の完了待ち・順番待ち・中止したタスクを含む |
| 応答中 | AI が実行している |
| 承認待ち | AI が許可していない操作の承認を待って止まっている（[10章](#10-承認と-undo)） |
| 完了 | AI が作業を終えた |
| 失敗 | AI の実行が失敗した。やり直すと未着手に戻る |

- 中止したタスクは未着手に戻すため、「中止」の状態は持たない。停止中の印を別に保存し、画面には「停止中（再開待ち）」と表示する（2026-10-25 決定）。
- タスクの「確認待ち」の状態は、確認を目標の単位にしたためなくした（2026-10-25 決定）。

#### 通知

- ユーザーの対応が必要になったときは、Bridge が**デスクトップ通知**を出し、タスクトレイのアイコンに印を付ける（2026-10-25 決定）。通知を選ぶと、Bridge のウィンドウでその目標・タスク・承認待ちを開く。Mod の実装後は、ゲーム内にも出す。
- 通知するのは次のとき。
  - 目標のタスクがすべて完了し、確認待ちになったとき（修正が終わったときも含む）。ゲームの再起動が必要なタスクがあれば、ここでまとめて知らせる。
  - 承認待ちになったとき
  - タスクが失敗したとき
- Bridge のウィンドウを見ている間は、デスクトップ通知を出さない。デスクトップ通知は、設定で止められる。

- 回答を待つ間、思考・ツールの実行・途中の発言を途中経過として表示する（プロバイダーがイベントとして出力する範囲で）。
- 作業ボード（ゲーム内の管理棟・Bridge のアプリの画面）には、目標ごとのタスクの状態、進み具合、経過時間、最新の途中経過の冒頭を表示する。承認待ちは、どの目標を見ていても気付けるように別枠で目立たせる。
- 以前の仕様では、会話の単位を「チャット」とし、別々のチャットを並行して実行していた（Mod の Config の `ai.maxConcurrentRequests`、初期値3 で上限を持ち、ワールドのセーブにチャット名・選択中のチャット・セッション ID を保存する方式）。

## 4. ゲームの情報を AI に渡す

ゲームの情報を AI に渡す方法は2つある。どちらも同じ取得処理を使う。

- **添付機能**: ①で、指示に最初から情報を添える（VSCode で選択範囲を AI に渡すのと同じ発想）。
- **ゲーム内 MCP サーバー**: ①②の両方で、AI が必要なときに自分でゲームの情報を取得し、操作する。

### 添付機能

| 添付する内容 | 取得方法 | 難易度 |
|---|---|---|
| 見ているブロック／エンティティ | 視線のレイキャストで種類・座標・NBT を取得 | 低 |
| 手持ちのアイテム | 手持ちアイテムの情報を取得 | 低 |
| プレイヤーの位置・向き・周囲のエンティティ | プレイヤー情報とワールドから取得 | 低 |
| 直前のログやエラー | `latest.log` を読む | 低 |
| スクリーンショット | ゲーム画面を画像として取得する | 中 |
| 範囲選択した領域 | `/pos1` `/pos2` などで2点指定（杖でも可） | 中 |
| スクリーンショットへの書き込み・範囲の指定 | 取得した画像の上で操作する | 高 |

- 取得処理はステップ1で作り、指示への添付はステップ6で入れる。範囲選択とスクリーンショットへの書き込みは、ステップ9以降（[14章](#14-実装の順序)）。
- 参照記法の案: `@looking`（見ているもの）、`@held`（手持ち）、`@selection`（選択範囲）。
- 大きい範囲はサイズ上限を決め、超えたら要約するか、構造物ファイル（structure NBT）に書き出してパスだけ渡す。
- AI には構造化したテキスト（JSON など）として添付する。スクリーンショットは画像として渡す（各 SDK が画像の入力に対応しているかは要確認）。

### ゲーム内 MCP サーバー

- **Mod のプロセスの中で MCP サーバーを動かす。** コアの機能とする。
- 目的: AI が、書いたコードをゲームの中で確かめるところまで、自分で進められるようにする。
- Claude Code と Codex の両方から使えるようにする。①では Bridge が実行する AI が、②では既存のアプリが接続する。
- Bridge を起動しなくても使える。
- 通信は**ローカルの HTTP ベースの MCP**を基本とする（MCP の Streamable HTTP トランスポートを想定）。
- **localhost にだけバインド**し、外部のネットワークに公開しない。
- ツールは「**読み取り専用**」と「**変更あり**」（ゲームの状態を変えるもの）に分けて提供する。
- **ポートは固定し、設定で変更できるようにする**（2026-11-01 決定）。既存のアプリに登録した接続先を、ゲームの起動ごとに書き換えずに済むようにする。使用中の場合は理由を表示し、勝手に別のポートへ切り替えない。初期値・設定項目・接続情報は [今回の実装仕様](#今回の具体的な実装仕様2026-11-01-承認) に従う。
- **MCP の認証トークンは自動生成して保存し、次回も使う**（2026-11-01 決定）。ワールドのセーブや Git 管理下には置かず、ユーザー専用の場所に保存する。Bridge には Mod から自動で渡す。保存先と認証手順は [今回の実装仕様](#今回の具体的な実装仕様2026-11-01-承認) に従い、Bridge 自身の WebSocket 接続用トークンとは別に扱う。

#### 動作する場所

- MCP サーバーは**論理サーバー側**で動かす。シングルプレイでは統合サーバー、マルチプレイでは専用サーバー（`runServer` など）の JVM で動く。マルチプレイでの動作確認にも同じ仕組みで対応するため。
- ワールドの状態（ブロック・ブロックエンティティ・エンティティなど）は、論理サーバーから直接取得する。
- クライアントにしかない情報（スクリーンショット、画面の表示、開いている GUI、クライアントのログなど）は、論理サーバーからパケットでクライアントに要求して取得する。対象のクライアントにも PotamAId が入っている必要がある。
- クライアントの情報を取るツールは、対象のプレイヤーを指定できるようにする。省略したときは次のように扱う。

| 状況 | 対象 |
|---|---|
| シングルプレイ | ローカルのプレイヤー |
| マルチプレイで、接続しているのが1人 | そのプレイヤー |
| マルチプレイで、接続しているのが2人以上 | ユーザーに確認をとってから決める |

- 確認のとり方は、MCP クライアントが対応していれば MCP の elicitation（サーバーからユーザーに入力を求める仕組み）を使い、対応していなければ接続中のプレイヤーの一覧を付けたエラーを返して、AI からユーザーに尋ねてもらう想定とする。Claude Code・Codex が elicitation に対応しているかは要確認。
- マルチプレイでは、他のプレイヤーのクライアントも対象にできる（サーバー側では対象を制限しない）。PotamAId は開発用の依存として使い、一般に公開する配布物には含めないため。また、クライアントの情報を返すには、そのクライアントにも PotamAId が入っている必要がある。
- 情報を送りたくないプレイヤーは、**クライアント側の設定**で、自分のクライアントからの情報の提供をブロックできる。初期値は「提供する」とする。ブロックしている場合、ツールはブロックされたことを示すエラーを返す。
- ブロックの粒度（すべてまとめてか、スクリーンショット・ログなど種類ごとか）と、設定項目の名前は未決定。
- MCP サーバーは論理サーバーの起動とともに始まり、停止とともに終わる。**論理サーバーが動いていない間は使えない。** Minecraft の中で開発することがコンセプトのため、これを仕様とする。
  - シングルプレイでは、ワールドを開いていない間（タイトル画面にいる間やゲームの停止中）がこれに当たる。
  - 専用サーバーの構成では、サーバーが動いていれば使える。ただし、クライアントの情報を取るツールは、対象のクライアントが接続している間だけ使える。

#### 最初に提供するツール（2026-11-01 決定）

- `get_player_snapshot` を、引数なしの読み取り専用ツールとして提供する。今回のシングルプレイではローカルプレイヤーを対象とし、プレイヤー選択は設けない。
- 既存の `GameInformationService` と `PlayerSnapshot` を利用し、プレイヤー名・UUID、座標・向き・ディメンション、両手のアイテム ID・個数を JSON として返す。取得できない場合は理由を含むエラーとし、古い情報で代用しない。
- Bridge を使わない既存の AI アプリには、利用者が初回に接続先とトークンを登録する。Mod はユーザー専用の場所に接続設定ファイルを用意し、その内容を使った登録手順をこの仕様書にまとめる。トークンはゲーム内チャットとログに表示しない。ファイルの保存先と形式は [今回の実装仕様](#今回の具体的な実装仕様2026-11-01-承認) に従う。

#### 読み取り専用ツールの追加（2026-11-03）

`get_player_snapshot` に加えて、次の3つを引数なしの読み取り専用ツールとして追加した（`readOnlyHint: true`、追加プロパティなし）。ツールの追加のみで、既存のツール名・設定名は変えていない。いずれも `GameInformationService` を通して取得し、タイムアウトは `mcp.requestTimeoutSeconds`（既定 5 秒）を使う。取得できない場合は、内部の例外全文を含めない理由つきのツールエラーを返し、古い情報で代用しない。

| ツール | 取得する場所 | 返す内容（`structuredContent` と同じ JSON のテキストも返す） |
|---|---|---|
| `get_target_block` | 論理サーバー | `hit`（見ているブロックがあるか）、`dimension`、`position`（`x`・`y`・`z`）、`blockId`、`state`（ブロック状態のプロパティ名と値）、`blockEntity`（`typeId`・`nbt`・`truncated`。ブロックエンティティがある場合のみ）。何も見ていなければ `hit: false` だけで、エラーにはしない |
| `get_mod_environment` | 論理サーバー | `minecraftVersion`、`neoForgeVersion`、`javaVersion`、`mods`（`id`・`name`・`version`。`minecraft`・`neoforge` 自体も含む。ID 順） |
| `get_game_logs` | 論理サーバーの JVM のログ | `file`（`logs/latest.log`。絶対パスは返さない）、`totalBytes`、`truncated`、`text` |

- **`get_target_block` は論理サーバーだけで足りるため、クライアントへの往復は設けない。** プレイヤーの目の位置と向きはサーバーが持っており、サーバー側のレイキャスト（到達距離は `blockInteractionRange`、流体は無視）で判定できる。クロスヘア上のブロックとはまれに数ピクセル分ずれる場合がある。
  - `blockEntity.nbt` は SNBT 文字列で、16384 文字を超える分は切り詰めて `truncated: true` にする（チェストの中身など大きいものを丸ごと渡さないため）。サーバースレッドでは独立した NBT のコピーを作るところまでにし、巨大な NBT の文字列化と切り詰めは別スレッドで行う（メインスレッドを長く止めないため）。
- **`get_game_logs` は `<ゲーム実行ディレクトリ>/logs/latest.log` の末尾 32 KiB を返す。** 超えた場合は古い側を切り捨てて `truncated: true` にする。読み始め位置が行の途中のときだけ、最初の改行までを捨てる（ちょうど行頭なら先頭の行を残す）。ゲームの状態は読まないため、サーバースレッドではなく専用の別スレッドで読み、メインスレッドを止めない。ファイルがない・読めない場合は「ログファイルを読み取れません」のエラーにする。
  - シングルプレイでは論理サーバーとクライアントが同じ JVM のため、このログにクライアントの出力も含まれる。専用サーバーの構成ではサーバー JVM のログだけで、クライアントのログの取得は別の段階（クライアントへのパケット）で扱う。
  - ログ中の `Bearer` の後ろに空白・タブで続くトークン文字列は、長さにかかわらず `Bearer [REDACTED]` に置き換える。Mod 自身は認証トークンをログへ出さない設計（接続設定の読み書きに失敗した場合も、理由の文言だけをログに出す）だが、念のための二重の対策である。
  - **ログにはユーザー名・ファイルのパス・他の mod の情報が含まれうる。** AI に渡すと、その AI のサービス（外部）に送られる。利用者は次を守る。
    - 公開してよいか分からない環境（実名のユーザー名のパス、他人のサーバーのログなど）では、AI に `get_game_logs` を呼ばせない。MCP クライアント側でこのツールの自動承認を許可しない設定にし、呼ぶたびに確認するのが安全。
    - AI が出力した内容を、Issue や共有チャットにそのまま貼る前に、ユーザー名とパスを確認する。
    - マルチプレイでは、他のプレイヤーの名前や IP アドレスがログに含まれる場合がある。

手動での確認手順（作者が実機で行う。Claude Code・Codex で接続済みの `potamaid_game` を使う）:

1. シングルプレイのワールドを開き、`tools/list` 相当の一覧（Claude Code なら `/mcp`）に `get_player_snapshot`・`get_target_block`・`get_mod_environment`・`get_game_logs` の4つが出て、すべて読み取り専用であることを確かめる。
2. チェストやかまど（ブロックエンティティを持つブロック）を見ながら「見ているブロックを教えて」と尋ね、`blockId`・`position`・`state`（向きなど）・`blockEntity.nbt` が実際の内容と合っていることを `F3` の表示と照らす。次に、空や遠くを見て、`hit: false` が返ることを確かめる。
3. 「読み込まれている mod と Minecraft・NeoForge のバージョンを教えて」と尋ね、`mods` に `potamaid`・`minecraft`・`neoforge` が含まれ、バージョンが `mod/gradle.properties` と一致することを確かめる。
4. 「直近のログを見て」と尋ね、`logs/latest.log` の末尾が返ること、`truncated` が実ファイルのサイズ（32 KiB 超か）に合っていること、`text` に認証トークン（`mcp.json` の `Authorization` の値）が含まれないことを確かめる。確かめるときは、`text` を `Bearer` で検索する。
5. ワールドを閉じてタイトル画面に戻ってから各ツールを呼び、サーバー停止のエラーが返ることを確かめる。

静的検証（Minecraft を起動しない）は `mod/` の `gradlew.bat build`（`testGameMcp` を含む）で行う。ブロック・mod 一覧の取得は GameTest（`GameInformationTests`、`gradlew.bat runGameTestServer -PgameTests`）で確かめる設計だが、このコミットの時点では実行していない。

#### 想定するツール

| ツール（仮の名前） | 種類 | 取得する場所 | 内容 |
|---|---|---|---|
| `get_player_position` | 読み取り専用 | 論理サーバー | プレイヤーの座標・向き・いるディメンション |
| `get_target_block` | 読み取り専用 | 論理サーバー（実装済み。[読み取り専用ツールの追加](#読み取り専用ツールの追加2026-11-03)） | 見ているブロックの種類・座標・状態・ブロックエンティティの NBT |
| `capture_screenshot` | 読み取り専用 | クライアント | ゲーム画面のスクリーンショット |
| `get_game_logs` | 読み取り専用 | 論理サーバー・クライアント（論理サーバー側は実装済み） | 直近のログ・エラー（`latest.log` など）。専用サーバーの構成では JVM ごとに別のログになる |
| `get_mod_environment` | 読み取り専用 | 論理サーバー（実装済み） | Minecraft・NeoForge のバージョン、読み込まれている mod の一覧など |
| コマンドの実行 | 変更あり | 論理サーバー | `/reload`、`/give`、GameTest など |
| リソースの再読み込み | 変更あり | クライアント | テクスチャ・モデル・翻訳の再読み込み（F3+T 相当） |

- ツール名と入出力の仕様、取得する場所の分担は、実装時に調整してよい。手持ちのアイテムや周囲のエンティティなど、添付機能で取得する情報も必要に応じてツールにする。
- 変更ありのツールの具体的な一覧は未決定。
- ツールが読み取り専用か変更ありかは、MCP のツールの注釈（`readOnlyHint` など）でも MCP クライアントに伝えることを想定する。
- 変更ありのツールを実行する前の確認は、まず MCP クライアント（Claude Code・Codex）のツールの承認の仕組みに従う。PotamAId 側で追加の確認を設けるかは未決定（[10章](#10-承認と-undo)）。

#### 安全対策

- localhost への接続でも、ブラウザなど別のアプリから要求を送られる可能性がある（DNS リバインディングなど）。**認証トークンを通信のヘッダーで確認し、URL とログには含めない**（2026-11-01 決定）。今回、ブラウザのページから直接接続する用途は対象にせず、`Origin` ヘッダーが付いた要求は拒否する。Mod と Bridge の WebSocket にも同じ方針を適用する。
- スクリーンショットやログには、ユーザー名やファイルのパスなどが含まれる場合がある。AI に渡すと外部のサービスに送られることを、利用手順に明記する。マルチプレイでは、他のプレイヤーの画面やログも送られる場合があることを含める。

#### スレッド

- MCP の要求は通信用のスレッドで受け、ゲームの状態を読み書きする処理は論理サーバーのメインスレッドへディスパッチして、結果を待って返す。
- クライアントの情報は、論理サーバーからパケットで要求する。クライアントでは、画面に関わる処理（スクリーンショットなど）を描画スレッドで実行し、結果をパケットで返す。
- ディスパッチした処理やクライアントの応答が終わらない場合（ワールドの読み込み中、クライアントの切断など）に備えて、タイムアウトを設ける。

## 5. PotamAId Bridge

- Minecraft とは独立した**ローカルプロセス**として動作する。
- ①で AI を実行するための中継役で、②では使わない。

### 責務

- Claude Code・Codex の実行管理
- 目標・タスク・相談と、AI のセッションの管理（[3章](#目標タスク相談)）
- 計画の作成と、承認された計画に沿ったタスクの実行順の管理（編集タスクは目標ごとの worktree で、読み取り専用の実行とともに上限まで並行）
- 目標の worktree の作成・タスクごとのコミット・ゲームを起動するディレクトリへの反映（[3章](#worktree-での並行実行)）
- ユーザーの対応が必要になったときの通知（[3章](#通知)）
- AI の実行イベント・進捗の取得
- Minecraft Mod への進捗の通知
- AI の実行のキャンセル
- Minecraft の再起動時の接続管理
- ユーザーの承認が必要な操作の管理
- アプリの画面の提供（[アプリの画面](#アプリの画面)）

### Mod との通信

- **Mod のクライアント側から Bridge へ接続する**。ゲームを再起動したら、クライアントから再接続する。
- クライアントから接続するため、ワールドを開く前（タイトル画面など）でも、目標・タスク・相談の状態、進捗、承認の待ちを確認できるようにする。
- 論理サーバーは Bridge と通信しない。指示を出せるのは、Bridge と同じ PC で動くクライアントを操作している開発者本人だけになる（[12章](#12-安全性と利用範囲)）。
- 通信は **localhost の WebSocket** で行う。Bridge が WebSocket のサーバー、Mod のクライアントが WebSocket のクライアントになる。Mod 側は Java 21 の標準ライブラリ（`java.net.http`）の WebSocket のクライアントを使い、依存ライブラリを増やさない。
- メッセージは JSON とする。接続確認・ゲーム状態・エラーは [接続の実装仕様](#今回の具体的な実装仕様2026-11-01-承認)、ゲーム内の相談と状態確認は [ゲーム内コマンドの実装仕様](#ゲーム内の相談と状態確認2026-11-01-追加) に従う。
- MCP サーバーと同じく、localhost にだけバインドし、接続の認証を設ける。

- **接続情報のファイル**（2026-11-01 決定）: Bridge が起動時に、ユーザー専用の場所へ接続情報（ポート番号と接続用のトークン）のファイルを書き出し、Mod はそれを読んで自動接続する。localhost の空いているポートを使い、トークンは Bridge の起動ごとに作る。利用者によるポート・トークンの手入力やログイン操作は不要とする。保存先・形式・アクセス権は [今回の実装仕様](#今回の具体的な実装仕様2026-11-01-承認) に従う。
- **Mod からの自動再接続**（2026-11-01 決定）: Bridge が後から起動した場合や再起動した場合も、Mod が接続情報ファイルを読み直して再接続する。Bridge の画面にはゲームとの接続状態を表示する。接続のみの初期段階ではゲーム内の進捗表示を含めず、その後のコマンド追加で状態・履歴の取得を加えた。切断中の進捗の自動再送は引き続き対象外。

- **プロトコルのバージョン**（2026-11-01 決定）: Mod と Bridge の通信仕様にバージョン番号を付け、接続時に照合する。対応していない組み合わせでは接続を止め、更新が必要だと分かる理由を表示・記録する。接続のみの初期実装は `1`。ゲーム内コマンドの追加で現在は `2` に更新し、Mod と Bridge の両方を更新して使う。MCP の標準プロトコルの番号とは別に扱う。

進捗の再送と専用サーバーでの接続先の受け渡しは、後の段階で確認する。

- **進捗の再送**: 進捗のイベントに連番を付け、再接続したときに Mod が受け取り済みの位置を伝えて、続きだけを送ってもらう。
- **MCP の接続先の受け渡し**: 今回のシングルプレイでは、Mod のクライアントが MCP の接続先を `game_state` で Bridge に伝える方式を承認済み（[今回の実装仕様](#今回の具体的な実装仕様2026-11-01-承認)）。専用サーバーでは、クライアントがサーバーの MCP のポートを知らないため、サーバーからパケットで教えてもらう案を後の段階で確認する。

### ゲームの再起動をまたいだ継続

- ゲームが終了・再起動しても、実行中の AI タスクを可能な範囲で継続する（[8章](#8-minecraft-の再起動への対応)）。
- 進捗のイベントは Bridge が保持し、再接続した Mod に送る。どこまで遡って送るかは未決定。

### 扱う範囲

- **1つの Bridge で、複数の対象mod（プロジェクト）と複数のゲームを扱う。**
- 目標・タスク・相談は対象modごとに分けて管理する。接続してきたゲームの対象modは、**ゲームの実行フォルダーを含む Bridge 登録先が1つに決まる場合に自動設定する**（2026-11-01 追加依頼）。候補が複数・未登録の場合や、別の Git リポジトリ・worktree の境界をまたぐ場合は自動で選ばず、理由を表示する。従来の `bridge.projectRoot` は任意の明示指定として残し、指定時は登録先との完全一致を優先する。詳細は [初回設定の自動化](#対象modの初回設定の自動化2026-11-01-追加) に従う。
- 同時に接続しているゲームごとに、その対象modの目標・タスク・相談の状態と進捗を送る。
- Bridge が実行する AI には、その対象modのゲームの MCP サーバーを接続する。
- **今回の同時接続は、対象modごとにゲーム1つまでとする**（2026-11-01 決定）。別の対象modのゲームは同時に接続できる。同じ対象modの2つ目のゲームには理由を示し、AI の接続先を勝手に切り替えない。同じ対象modの複数ゲームから接続先を選ぶ機能は後回しにする。
- 編集タスクは目標ごとの worktree で実行する。編集タスクと読み取り専用の実行（計画の作成・調査タスク・相談）の同時実行数の上限は、それぞれ対象modごとに Bridge の設定で持つ（[3章](#目標の進め方)）。

### セッションの永続化

- Bridge の状態は **SQLite** に保存する。トランザクションで書き込めるため、Bridge が異常終了してもデータが壊れにくく、進捗のイベントを連番で保存して再送に使うのにも向いているため。
- 保存する内容: 対象mod、目標と計画、目標のブランチと worktree の場所、タスクとその状態・依存関係・重さ・実際に使った実行の設定とモデル、相談、各プロバイダーのセッション ID（タスク・相談・計画ごと）、まだ AI に渡していない追加の指示、進捗のイベント、実行の設定（プロファイル）、設定。
- 承認の待ちは、AI のプロセス（Codex app-server）と一緒に消えるため保存しない。
- 会話の本文は、各プロバイダーの通常のセッション保存先に残す。ただし、進捗のイベントには AI の発言も含め、タスクの詳細と相談の表示に使う（プロバイダーから会話を読み直さずに表示するため）。進捗のイベントをどれだけ残すか（保存期間・件数）は未決定で、今は消さない。
- 保存場所は、Bridge のアプリのユーザーデータのディレクトリ（`bridge.sqlite`）とする。
- SQLite は、Electron に含まれる Node.js の組み込みの **`node:sqlite`** を使う（2026-10-25 決定）。ネイティブモジュールを Electron 向けにビルドし直す手間がないため。Node.js では実験的な機能の扱いのため、Electron の更新時に API の変更を確かめる。
- Bridge を終了・異常終了したときに実行中だったタスクと相談は、次の起動で**中止と同じ扱い**にする（2026-10-25 決定）。タスクは未着手に戻し、途中経過に中断したことを残す。ユーザーが再開するまで自動では実行しない。計画の作成中だった目標は、前の計画があれば計画の確認に戻し、なければ「計画の失敗」にする。

### Bridge の MCP ツール

Bridge が実行する AI に、目標やタスクを調べるツールを渡す（2026-10-25 決定）。

- Bridge が **MCP サーバー**（Streamable HTTP）を動かし、計画の作成・タスク・相談のセッションに接続する。Claude Agent SDK にも MCP サーバーとして渡せるため、プロバイダーごとの独自のツールの仕組み（Codex の dynamic tools など）は使わない。
- localhost にだけバインドし、ポートは起動ごとに空いているものを使う。起動ごとに作るトークンを `Authorization` ヘッダーで確かめる。
- Codex には、スレッドの開始・再開の設定の上書き（`config` の `mcp_servers.potamaid_bridge`）で渡す。利用者が `config.toml` に書いた MCP サーバーはそのまま使える。
- ツールはすべて読み取り専用で、セッションの範囲だけを返す。計画の作成とタスクのセッションでは、その目標の対象mod（目標を省いたときはその目標）、相談では対象modが範囲になる。

| ツール | 内容 |
|---|---|
| `list_goals` | 対象modの目標の一覧（題名・状態・タスクの進み具合） |
| `get_goal` | 目標の依頼文・計画の方針・タスクの一覧 |
| `get_task` | タスクの内容・状態・結果の報告・失敗の理由 |

- 実装には MCP の公式の TypeScript SDK（v2 の `@modelcontextprotocol/server` と `@modelcontextprotocol/node`）を使う。

### 承認

- AI がユーザーの承認を必要とする操作（許可していないツールの使用など）は、Bridge が受け取って管理する。ゲーム内と Bridge のアプリの画面の両方で承認を求め、どちらで承認してもよい。
- ゲームが起動していない間も、Bridge のアプリの画面で承認できる。
- AI からの質問（Codex の `item/tool/requestUserInput`）と、MCP サーバーの入力要求（`mcpServer/elicitation/request`。入力フォームと URL を開く要求）も、ユーザーの対応を待って止まるものとして承認待ちにまとめる（2026-10-25 決定）。タスクの状態は「承認待ち」にし、相談と計画づくりでは状態を変えずに承認待ちの枠とその画面に出す。秘密の回答（パスワードなど）は途中経過に残さない。
- 目標の計画の承認（[3章](#目標の進め方)）も、同じくゲーム内と Bridge のアプリの画面で行える。同じ承認に両方から回答したときは、先に届いた回答だけを有効にする（[14章](#ゲーム内の承認操作2026-11-03-決定)）。

### 実装言語

- Bridge は **TypeScript** で実装する。Claude Agent SDK に TypeScript 版があり、Codex app-server も CLI から TypeScript の型定義を生成できるため。

### 起動と配布

- Bridge は **Electron のデスクトップアプリ**として作る。TypeScript の SDK をそのまま使え、Node.js を同梱できるため。
- **Bridge を動かすための実行環境（Node.js など）は、アプリに同梱する。** 利用者に別途用意させない。
- **Codex・Claude の CLI は、再配布条件を満たしたうえで、パッケージに含まれる実行ファイルを同梱して使う方針とする。** Claude の再配布条件は未確認のため、確認が済むまで配布物への同梱は行わない（[7章](#7-認証とライセンス)）。設定で、利用者が導入した CLI の実行ファイルのパスを指定することもできる（Claude Agent SDK は `pathToClaudeCodeExecutable`）。
- **認証は、利用者が各 CLI の公式の手順で済ませておく**（Codex は `codex login`）。Bridge の画面にはログインの機能を設けない。同梱の Codex の CLI も、同じユーザー・同じ `CODEX_HOME` と認証情報の保存方式で動かし、公式のログイン情報を再利用する。保存先は `~/.codex` 配下のファイルまたは OS の資格情報ストアなど、設定により異なる（[公式の認証資料](https://learn.chatgpt.com/docs/auth)）。ログインには利用者が導入した Codex の CLI を使う（[7章](#7-認証とライセンス)）。
- **Bridge が動いていることが、利用者に常に分かるようにする。** 利用者が明示的に起動・終了し、Mod から自動で起動しない。ゲームを閉じたあとに、利用者が気付かないまま裏で動き続ける状態を作らない。
- ゲームを閉じても AI のタスクは続ける（[8章](#8-minecraft-の再起動への対応)）が、それは Bridge が見える形で動いている間に限る。
- **ウィンドウを閉じたら、通知領域（タスクトレイ）にアイコンを出して動き続ける。** 終了は、アイコンのメニューなどから明示的に行う。
- アプリの画面で、ゲームの外でも目標・タスク・相談の状態と進捗を確認し、指示と承認を行えるようにする（[アプリの画面](#アプリの画面)）。
- Bridge の本体（AI の実行・セッション管理・Mod との通信）と画面は分けて作り、画面はゲーム内 UI と同じく Bridge につながるクライアントの1つとする案がある。
- 実行中・順番待ちのタスクがあるときに終了しようとした場合は、**警告を表示する**。
- 使われていないときの扱いは未決定。

### アプリの画面

ゲームを閉じている間も作業の状態を見て操作できるよう、ゲーム内 UI と同じ操作をアプリの画面でも行えるようにする。

| 部分 | 内容 |
|---|---|
| ヘッダー | 対象modの切り替え、実行数（編集中のタスク・読み取り専用の実行）、設定 |
| サイドバー | 対象modの「目標」の一覧（進み具合と状態）と「相談」の一覧 |
| 目標のボード | 選んだ目標のタスクを「未着手 → 応答中 → 完了」の列で表示する。失敗したタスクがあるときだけ「失敗」の列を出す。横幅が足りないときは横にスクロールし、完了の列は小さく表示する。目標が確認中のときは、ボードの上に確認の枠（再起動が必要なタスク、目標の「完了にする」、目標への修正の指示）を出す |
| 計画の確認 | 計画が承認待ちの目標を選ぶと表示する。タスクの編集・削除・追加（編集と調査の切り替え、重さ・実行の設定の変更を含む）、作り直しの指示、承認ができる |
| タスクの詳細 | ボードのカードを選ぶと表示する。タスクの内容と依存関係、途中経過、承認、そのタスクへの追加の指示 |
| 相談 | ボードとは別に、チャットの形で表示する |
| 承認待ち | 対象modの承認待ちを、ボードの上に別枠で表示し、その場で許可・拒否できる |

- **タスクトレイのメニュー**: 状態の要約、「ウィンドウを開く」「承認待ちを確認」「すべての実行を中止」「設定」「Bridge を終了」。承認待ち・確認待ちの目標・失敗したタスクがあるときは、トレイのアイコンに印を付ける。
- ライトとダークのテーマを用意する。UI のライブラリは daisyUI（Tailwind CSS のプラグイン）を候補とする。
- 再起動が必要な変更は表示だけ行い、Bridge の画面からゲームを再起動する機能は、自動再起動の方式（[9章](#再起動の待ち時間を減らす)）が決まってから検討する。

### リポジトリの構成

- Bridge は **このリポジトリに含める（モノレポ）**。プロトコルを変えるとき、Mod と Bridge を1つの PR で直せるようにするため。
- Bridge のソースは、リポジトリの直下の `bridge/` などのディレクトリに置く想定とする（名前は未決定）。
- Mod と Bridge はバージョンを分けてリリースする想定とする。そのためには release-please の設定とタグの形式（例: `potamaid-v0.2.0` と `bridge-v0.1.0`）の変更が必要になる。release-please が管理するファイルとタグに関わるため、変更するときは作者に確認する。
- Electron のアプリのビルドには OS ごとの実行環境が必要になるため、CI は Mod のビルドとは別のワークフローに分ける想定とする。

### 今後検討する事項

- **配布方法**: OS ごとのインストーラーの形式、コード署名、アップデートの方法。
- **CLI の案内**: 指定した CLI が見つからない場合や、ログインしていない場合の案内。

## 6. AI プロバイダー

- **Claude Code と Codex の両方に対応する**ことを目標とする。
- Bridge の中では、プロバイダー固有の実装を共通のインターフェースで抽象化する。共通のインターフェースで扱うもの（案）: 実行の開始、進捗のイベント、セッションの作成・再開、キャンセル、承認の要求。
- 先に Codex に対応し、Claude（Claude Agent SDK）はその後に対応する（[14章](#14-実装の順序)）。
- アプリの画面やゲーム内の表示では、Claude のプロバイダー名を「Claude」と表示し、「Claude Code」とは表示しない（[Claude Code](#claude-code) のブランドのガイドライン）。

### Codex

| 項目 | 方針 | 状態 |
|---|---|---|
| 実行の方式 | **Codex app-server**（`codex app-server`）を使う。TypeScript SDK は使わない | 決定 |
| 認証 | 利用者が `codex login` で済ませた ChatGPT アカウントのログインを使う | 決定 |
| 利用枠 | 利用者の ChatGPT のプランの利用枠で実行する | 決定 |
| Sign in with ChatGPT | 公式が勧める、アプリ向けの認証の仕組み。将来の移行先として検討する | 将来 |
| API キー | API キー方式も選べるようにする | 決定 |
| セッション・進捗・承認 | スレッドの作成・再開、途中経過のイベント、承認の要求に対応する | 決定 |

- **app-server を使う理由**: TypeScript SDK は内部で `codex exec`（対話しない実行モード）を動かすため、AI が承認を求めても、その要求をアプリで受け取れない。app-server では、コマンドの実行やファイルの変更の前に、承認の要求（`item/commandExecution/requestApproval`・`item/fileChange/requestApproval`）がアプリに届き、アプリが許可・拒否を返せる。公式も、承認・履歴・途中経過を含む深い組み込みには app-server を、自動化や CI には SDK を案内している。
- **注意**: app-server は実験的な機能で、本番での利用はサポート外とされている。Codex の更新でプロトコルが変わる可能性があるため、Bridge では app-server とのやり取りをプロバイダーの実装の中に閉じ込め、型定義は CLI から生成する。
- Bridge は Codex の実行ファイルを子プロセスとして起動し、標準入出力で JSON-RPC をやり取りする。設定で実行ファイルのパスを変えられるようにする。
- 今は、設定で指定したパス、なければ PATH の `codex` を使う（2026-10-25 決定）。同梱は、配布の準備のときに LICENSE・NOTICE を確認してから行う。
- app-server の型は `codex app-server generate-ts` で生成して Bridge のリポジトリに含め（`pnpm gen:codex`）、Codex を更新したら生成し直す。
- **モデルと思考量（reasoning effort）**: 選択肢は `model/list` から取得する。どのタスクにどれを使うかは [実行の設定とモデルの選び方](#実行の設定とモデルの選び方) に従う。
- **タイムアウト**: app-server への要求（起動・セッションの開始など）の応答と、ターンの途中で Codex から何も届かない状態の長さに上限を設け、超えたら失敗にする。初期値は 60 秒と 10 分で、設定で変えられる（2026-10-25 決定）。承認待ちの間は無応答の時間を数えない。
- **Windows の文字化け**: Codex がコマンドを動かす疑似コンソールは CP932 のままで、Codex はその出力を UTF-8 として読むため、コマンドの出力の日本語が文字化けする（Codex 側の問題。2026-10-25 時点）。Bridge では、Codex を起動する前の `chcp 65001` では直らないことを確かめた。コマンドの一覧には Codex が解析した操作（読み取り・一覧・検索）か、シェルの包みを外したコマンドを出し、元のコマンドと出力は詳しい内容に残す。
- 参考（2026-10-25 時点の[app-server の公式資料](https://learn.chatgpt.com/docs/app-server)による。実装前に再確認する）:
  - ローカルで動くアプリやオープンソースのアプリは、app-server の認証（利用者の ChatGPT のログイン）を使い続けてよいが、Sign in with ChatGPT への移行が勧められている。**商用のサービスやサーバーで提供するサービスでは、これまでも認められていない。** PotamAId は無料・オープンソースで利用者の PC で動くため、前者に当たると判断する。有料化やサーバーでの提供をする場合は、この判断を見直す。
  - [Sign in with ChatGPT のプラン利用](https://developers.openai.com/siwc/token-sharing-open-source)は、オープンソースやローカルで動くアプリ向けに案内されている（OAuth でアプリを登録し、利用者が同意する）。対象プランと制限は、導入時に公式資料で再確認する。
  - 自動化の用途では API キーを基本にするよう案内されている。API キーでは、ChatGPT のプランではなく API の料金がかかる。
  - Codex の SDK と CLI のライセンスは Apache-2.0。再配布時は、採用する版の LICENSE・NOTICE・依存物の条件を確認して満たす。ライセンスによる再配布の許可と、ChatGPT の認証・サービスの利用条件は別に確認する。

### 実行の設定とモデルの選び方

タスクごとに、使うモデルを選べるようにする。利用者が指定するほか、計画のときに自動で決まるようにする（2026-10-25 決定）。

- **実行の設定（プロファイル）**: プロバイダー・モデル・思考量の組に名前を付けて、Bridge の設定に登録する。例: 「標準（Codex の既定のモデル・思考量 medium）」「重い（Codex・思考量 high）」。
- **タスクの重さ**: AI が計画を作るときに、各タスクに4段階の重さを付ける（2026-10-25 決定）。モデルと思考量の組み合わせで段階を分けられるようにするため。値の名前は仮に `light`・`standard`・`heavy`・`max` とする。
- AI には具体的なモデル名を付けさせない。利用者ごとに使えるモデルが違うため。
- 重さごとにどの実行の設定を使うかは、Bridge の設定（対象modごと）で決める。
- 利用者は、計画の確認のときに、タスクごとに重さか実行の設定を変えられる。
- タスクに使う実行の設定は、次の順で決める: タスクで直接指定したもの → 重さに対応する実行の設定 → 目標の既定 → Bridge の設定の既定。計画の作成と相談は、目標・相談の既定を使う。
- 目標と相談の既定は、作るときに変えられる。以前の仕様で目標に持たせていたモデルと思考量は、目標の既定として引き継ぐ（2026-10-25 決定）。
- 目標・相談の既定でモデルか思考量だけを指定したときは、指定しなかった方に Bridge の設定の Codex の既定（モデル・思考量）を使う。以前の目標の指定と同じ扱いにするため。消された実行の設定を指しているときは、次の段階に進む。
- タスクへの追加の指示は同じセッションの続きで実行するため、プロバイダーは変えられない。モデルと思考量は、同じプロバイダーの中なら変えられる見込み（Codex は `turn/start` でモデルを上書きできる。要確認）。今は、前回の実行の設定のまま続ける。その実行の設定が消えたか、プロバイダーが変わっていれば、記録したモデルで続ける。
- **AI が重さを付けないタスクの重さは、`standard` とする。競合を解くタスクだけ `heavy` にする**（2026-10-25 決定）。計画の確認で利用者が追加したタスクと、目標への修正の指示がこれに当たる。AI が付けた重さは、種類によって補正しない。
- 未着手・失敗のタスクは、タスクの詳細で重さと実行の設定を変えられる。失敗したタスクをやり直す前に、重い設定に変えるのに使う。
- **失敗したタスクを、一段重い実行の設定で自動でやり直す機能は入れない**（2026-10-25 決定）。利用枠を使うため、利用者が重さを変えてやり直す。
- 実際に使った実行の設定とモデルはタスクに記録し、ボードのカードとタスクの詳細に表示する。設定を変えたあとでも、どのモデルで実行したか分かるようにするため。
- **LM Studio・Ollama などのローカル LLM には対応しない**（2026-11-01 決定）。2026-10-25 に、実行の設定の接続先としてローカル LLM を選べるようにした（Codex の `model_providers` をスレッドの `config` で渡す方式）が、うまく動かないことがあり、必要性も高くないため取りやめた。

## 7. 認証とライセンス

### 方針（決定）

- 利用者自身の Claude・ChatGPT のアカウント、または API キーを使う。
- PotamAId が利用者のパスワードを直接取得しない。
- 認証情報の保存・管理は、できるだけ公式の認証の仕組みに任せる。
- Codex・Claude の CLI は再配布条件を満たしてから同梱し、認証は利用者が各 CLI の公式の手順で済ませておく。Claude のサブスクリプションの適用条件は確認が必要。Bridge の画面にはログインの機能を設けない（[5章](#起動と配布)・[6章](#claude-code)）。
- Codex は、利用者の ChatGPT のログインを使う。PotamAId が無料・オープンソースで利用者の PC で動くことが前提（[6章](#codex)）。
- サブスクリプションの利用制限を回避しない。
- 利用制限に達しても、**ユーザーの明示的な許可なしに従量課金の API へ切り替えない**。

- Claude Agent SDK のサブスクリプション利用の PotamAId への適用条件と、同梱される実行ファイルを Electron のアプリに含めて配布する条件（Anthropic の商用利用規約）。
- Codex の採用する版の LICENSE・NOTICE・依存物の再配布条件。
- その他の依存ライブラリのライセンスの表示の方法。
- Codex の名前の表示に関するガイドライン（Claude は「Claude」と表示することに決定）。
- API キー方式を使う場合の、キーの受け渡し方法（環境変数・公式の保存先など）。

## 8. Minecraft の再起動への対応

Minecraft は、mod の開発中に頻繁に再起動されることを想定する。

| 状況 | 扱い |
|---|---|
| ゲームの終了 | Bridge の AI タスクは、原則として中断しない |
| ゲームの再起動後 | Mod から Bridge に再接続し、目標・タスク・相談の状態と進捗を受け取る |
| 論理サーバーが動いていない間の MCP | MCP サーバーも使えない（仕様）。シングルプレイでは、ワールドを開いていない間やゲームの停止中がこれに当たる。専用サーバーの構成では、サーバーが動いていれば使える（クライアントの情報は、対象のクライアントが接続している間だけ取得できる）。論理サーバーを起動し直したあとに MCP クライアントが再接続できるかは、Claude Code・Codex それぞれで検証する |
| 異常終了 | 別途定義する |

- AI の実行処理は、Minecraft のプロセスから切り離す。
- MCP サーバーは論理サーバーの中にあるため、論理サーバーが動いていない間は接続そのものができない。Minecraft の中で開発することがコンセプトのため、この間に要求を受け付ける仕組み（取得済みの情報を返すなど）は設けない。
- セッションの復元の範囲と、異常終了時（ゲーム・Bridge それぞれ）の扱いは、別途定義する。
- ゲーム情報を取得できなかった場合は、取得に失敗したことを AI に伝え、古い情報を現在の情報として返さない。**今回は、その失敗だけを理由に Bridge が AI の作業全体を自動中止する仕組みは設けない**（2026-11-01 決定）。将来は、ゲーム情報が作業に必須かを AI が判断し、必須であれば理由を示してタスクを一時停止できる仕組みを検討する。今回、その判断や停止・再開の仕組みは実装しない。

## 9. コードの反映とゲームの再起動

### ホットリロードの定義

**ホットリロード**は、ゲームを再起動せずに、編集したコード・データ・アセットを実行中のゲームに反映することとする。対象と反映の方法は次のとおり。

| 変更の種類 | 反映の方法 | 反映する JVM |
|---|---|---|
| メソッドの中身の変更 | クラスの差し替え（通常の JDK でも可能） | そのクラスを読み込んでいる各 JVM |
| メソッド・フィールドの追加など、クラスの構造の変更 | クラスの差し替え（JBR の場合） | 同上 |
| レシピ・ルートテーブル・タグなどのデータ | `/reload` | 論理サーバー |
| テクスチャ・モデル・翻訳などのアセット | リソースの再読み込み（F3+T 相当） | 各クライアント |

- シングルプレイでは、論理サーバーとクライアントが同じ JVM にある。専用サーバーの構成では、サーバーとクライアントの JVM ごとに反映が必要になる。
- データとアセットの再読み込みは、MCP の変更ありのツール（[4章](#4-ゲームの情報を-ai-に渡す)）として提供し、AI が自分で実行できるようにする。

### クラスの差し替えの手段

誰がクラスを差し替えるかは未決定。候補は次のとおり。

| 案 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| **A. IDE に任せる** | IntelliJ IDEA・VS Code などのデバッガーのホットスワップを使う。PotamAId は差し替えを行わない | 作る量が少ない。開発者が普段使う仕組みに乗れる | デバッガーで起動しておく必要がある。AI だけでは差し替えを完結できない |
| **B. Mod の Java エージェント** | AI がコンパイルしたあと、Mod が出力を読んで `Instrumentation.redefineClasses` で差し替える | ゲームの中で完結し、結果を MCP で返せる | エージェントの組み込み方と、FML のクラスローダーの上でどこまで動くかの検証が必要 |
| **C. Bridge が JDWP で差し替える** | ゲームをデバッグポート付きで起動し、Bridge が外から接続して差し替える | 複数の JVM（サーバーとクライアント）にまとめて反映できる。自動再起動とも相性がよい | デバッグポートを開いて起動する必要がある。Bridge の責務が増える |

- コンパイル（`gradlew compileJava` など）を誰が実行するか（AI・Bridge・IDE）も、差し替えの手段と合わせて決める。

### 再起動が必要なもの

- ブロック・アイテムなどの**新しい登録**（起動時に登録されて固定されるため）
- 新しいイベントリスナーの登録など、起動時にしか読み込まれない処理の変更
- クラスの差し替えに失敗した変更（通常の JDK での構造の変更など）

### JBR（JetBrains Runtime）

- JBR は**推奨とし、必須にはしない**。
- JBR のときは `-XX:+AllowEnhancedClassRedefinition` で、クラスの構造の変更も差し替える。
- 通常の JDK のときは、差し替えられない変更を再起動で対応する。

### 「再起動が必要」の判定

次の2つを組み合わせて判定する。

- クラスの差し替えを試した結果（失敗したら再起動が必要。差し替えの手段によって結果の受け取り方が変わる）
- AI による報告（構造化した出力で報告させる）。差し替えに成功しても、起動し直さないと反映されない変更（新しい登録など）を拾うため。

再起動が必要なときは、タスクの結果（ゲーム内・Bridge のアプリの画面）で知らせ、ゲーム内に再起動のボタンを出す。タスクごとには通知せず、目標が確認待ちになったときの通知でまとめて知らせる（[3章](#通知)）。

### 再起動の待ち時間を減らす

- 自動再起動の方式は未決定（技術検証で決める）。候補は次のとおり。
  - **ランチャー方式**: PotamAId が専用の起動タスクを用意する。ゲームが「再起動してほしい」という終了コードで終了したら、ビルドし直して起動し直す。
  - **自己再起動方式**: ゲームが自分の起動コマンドを読み取って新しいプロセスを起動し、自分は終了する。
  - **Bridge が担う方式**: ゲームの外で動き続ける Bridge が、ビルドとゲームの起動し直しを行う。
- 工業modの開発では登録の追加が多いため、自動再起動の優先度は高めにする。

## 10. 承認と undo

### 承認

- AI に許可する操作の制限と、承認が必要な操作の管理は、Bridge が行う（[5章](#5-potamaid-bridge)）。①ではゲーム内と Bridge のアプリの画面で承認を求める。②では既存のアプリの承認の仕組みに従う。
- 相談・計画の作成・調査タスクは読み取り専用で実行する。ファイルの編集、変更を伴うコマンドや MCP ツールの実行は許可せず、編集の承認で権限を広げない（[3章](#目標タスク相談)）。
- Codex の権限の設定への対応付け（2026-10-25 決定）:

| 実行 | `sandbox` | `approvalPolicy` | 意味 |
|---|---|---|---|
| 計画の作成・調査タスク・相談 | `read-only` | `never` | 承認を求めず、許可されない操作は失敗させる |
| 編集タスクの実行 | `workspace-write` | `on-request` | 作業ディレクトリの中は編集でき、サンドボックスの外の操作は承認を求める |

- Claude（Agent SDK）の権限の設定への対応付けは、対応するときに決める。
- MCP の変更ありのツール（[4章](#4-ゲームの情報を-ai-に渡す)）は、①②とも MCP クライアントのツールの承認の仕組みに従う。PotamAId 側で追加の確認を設けるかは未決定。
- 許可するツールの初期設定（以前の仕様の案: ファイルの読み書き、検索、`gradlew compileJava` など）は未決定。

### 反映のタイミング

- 以前の仕様にあった「先に反映（反映して試してから採用か戻すかを選ぶ）」と「承認してから反映」の切り替えは、クラスの差し替えの手段（[9章](#9-コードの反映とゲームの再起動)）と合わせて決め直す。

### 差分と undo

- 差分の確認と Git の操作は、VS Code などの既存の開発ツールで行うことを基本とし、ゲーム内での差分の表示や「採用」「戻す」の操作は必須にしない。
- 以前の仕様の undo の方式（指示を実行する前に、`git stash create` で作ったコミットを `refs/potamaid/...` に保存し、「戻す」で記録した状態にファイルを戻す。ユーザーのブランチにはコミットを作らない）を、PotamAId（Bridge）の機能として提供するかは未決定。
- 編集タスクは目標のブランチの worktree で実行し、Bridge がタスクごとにコミットする（[3章](#worktree-での並行実行)）。利用者のブランチには、ゲームを起動するディレクトリにコミットしない変更として反映する案のため、コミットは作らない。目標のブランチのコミットを、タスクごとの undo に使える。
- ワールドの変更の undo は難しめで、方式は未決定（開発用のワールドなので優先度は低め）。

## 11. 拡張システム

### 拡張で足せるもの

1. **MCP ツール**（例: テクスチャ作成の拡張なら、PNG を生成して assets に書き出すツール）
2. **ゲーム内 UI のタブ**（例: 生成したテクスチャのプレビュー）
3. **AI 向けの知識**（Claude Code・Codex のスキルや指示の断片。例: NeoForge 1.21.1 の API の使い方。AI が古いバージョンの API と混同するのを防ぐ）

### 拡張の単位

- 1・2 を含むものは、**PotamAId の API を使う別mod**にする（これも開発用の依存として入れる）。
- 3 だけのものは、**ファイル（スキルなど）として配布**する。

### 方針

- 最初の拡張は**テクスチャ作成**。生成した画像は通常のリソースとして書き出す。
- **早すぎる分割は避ける**。まず1つ目の拡張を実際に作り、必要になった API をコアに戻す。
- 拡張に権限を宣言させる仕組みは設けない（Java の mod は実際には制限できないため）。安全性は、MCP ツールの「読み取り専用／変更あり」の区別と、承認の仕組み（[10章](#10-承認と-undo)）で確保する。
- 拡張で足す MCP ツールも、PotamAId の MCP サーバーから提供する。ゲームの外で動く処理（画像の生成など）を、拡張の mod と Bridge のどちらに置くかは未決定。

## 12. 安全性と利用範囲

- チャットから AI を動かせることは、事実上「任意のコードを実行できる」のと同じなので、指示を出せる人を限定する。
- ゲーム内からの指示（①）は、**Bridge と同じ PC で動くクライアントの開発者本人だけ**が出せる。Bridge との通信をクライアント側だけに置くことで、これを保証する。
- **他のプレイヤーからの指示は、セキュリティの観点から実装しない。** マルチプレイでも、サーバーを経由して AI に指示する経路は設けない。
- MCP サーバーと Bridge は localhost からの接続だけを受け付け、認証や `Origin` の検証などの対策を検討する（[4章](#4-ゲームの情報を-ai-に渡す)・[5章](#5-potamaid-bridge)）。
- MCP のツールは「読み取り専用」と「変更あり」に分け、変更ありのツールは MCP クライアントの承認の仕組みに従って実行する（[4章](#4-ゲームの情報を-ai-に渡す)）。
- AI が編集するのは対象modのリポジトリと、その目標の worktree の中だけとし、変更は Git で戻せる状態にする。

### マルチプレイ（後回し）

将来、次の使い方に対応する。

- **専用サーバーでの動作確認**: 1人で、同じ PC で `runServer` と `runClient` を動かす。AI は1つのリポジトリを編集し、サーバーとクライアントの両方の JVM に反映する。
- **テストプレイを見ながらの調整**: 開発者が、自分の PC でサーバー・Bridge・自分のクライアントを動かし、他のプレイヤーに接続して遊んでもらう。指示は開発者のクライアントから出し、サーバー側のロジックを反映する。クライアント側のコードの変更は、相手に再接続や再起動をしてもらう。

複数人での共同開発（各クライアントへのコードの配布）は対象にしない。

- AI に指示できるのは開発者本人だけで、他のプレイヤーからの指示は受け付けない（上を参照）。
- MCP サーバーは論理サーバー側にあるため、専用サーバーでも同じツールを使える（クライアントの情報は、対象のクライアントから取得する）。
- MCP サーバーは localhost にだけバインドするため、AI（Bridge や既存のアプリ）はサーバーと同じ PC で動かす必要がある。

## 13. 工業mod・連携

- 工業modそのものや、Create・Mekanism などとの連携は、**PotamAId を使って別のリポジトリで作る**。PotamAId を実際に使って試す場にもなる。
- PotamAId 側は、その開発を**知識ファイル**（[11章](#11-拡張システム)の3）で支援する。
- 連携は、各modが公開している API やイベントを使う。連携ごとに、対象modの対応バージョンと API を調べてから実装する。
- NeoForge 1.21.1 には、エネルギー・流体・アイテムの受け渡しの仕組み（Capabilities）がある。工業mod側の設計時に調べて使う（詳細は要調査）。

### 今回の Mod・Bridge 連携の実装範囲（2026-11-01 決定）

- 今回は、Mod 内 MCP サーバーと、Mod クライアントから Bridge への接続、Bridge が実行する AI へのゲーム MCP 接続先の受け渡しまでを対象にする。仕様の確認を済ませ、作者が実装開始に合意してからコードと依存関係を変更する。
- 対応環境は、同じ PC で動かすシングルプレイとする。専用サーバーへの対応は後回しにし、共通コードとクライアント専用コードの分離は維持する。
- 最初のゲーム MCP ツールは、引数なしの読み取り専用ツール `get_player_snapshot` とする。プレイヤー名・UUID、座標・向き・ディメンション、両手のアイテム ID・個数をまとめて JSON で返す。フィールド名とエラーの扱いは、以下の実装仕様に従う。
- 利用者が Bridge の画面で現在地と手持ちを尋ねると、AI が起動中のゲームから情報を取得して回答できることを完了の目安とする。Mod の MCP は Bridge を起動しなくても使える。
- ゲーム内からの指示・進捗表示・承認・中止・再開、スクリーンショット・ブロック情報・ログの取得、ゲームの状態を変えるツールは今回の対象に含めない。
- ゲーム再起動後の状態復帰と進捗履歴の再送は後の段階に分ける。今回は、Bridge の接続・切断表示と、Mod から Bridge への自動再接続を含める。ゲーム MCP クライアント側の再接続は実機で確認する。
- Bridge の接続先の自動取得と対象modの初回設定は [5章](#mod-との通信) の方式を使う。今回のゲーム MCP の接続先・ポート・認証と Bridge への受け渡しは、以下の実装仕様に従う。

#### 今回の具体的な実装仕様（2026-11-01 承認）

作者は、この節の具体案を含めた仕様の確定と実装開始を承認した。実装は別のチャットで行う。この承認には、下記の `ws` と型定義の追加を含む。既存の依存関係の更新、commit・push・PR 作成、実機確認のための `runClient`・`runServer` の起動は含まない。以下は承認済みの仕様・実装方針・完了条件とする。

| 項目 | 内容 |
|---|---|
| Bridge の接続情報 | `<ユーザーホーム>/.potamaid/bridge.json`。JSON に `schemaVersion: 1`、`protocolVersion: 1`、`instanceId`、`url`、`token` を保存する。URL は `ws://127.0.0.1:<空きポート>/mod` |
| ゲーム MCP の接続設定 | `<ユーザーホーム>/.potamaid/games/<ゲーム実行ディレクトリの識別値>/mcp.json`。識別値は実在するゲーム実行ディレクトリの正規化した絶対パスの SHA-256 とし、ワールドを変えても同じ設定を使う。JSON は `schemaVersion: 1`、`url`、`headers`（`Authorization`）を持つ |
| MCP の初期接続先 | `http://127.0.0.1:38281/mcp`。複数の開発環境を同時に動かす場合は、それぞれの Mod 設定で異なる固定ポートを指定する |
| Mod の設定 | `Config.java` に、CLIENT 設定 `bridge.enabled`（初期値 `true`）・`bridge.projectRoot`（空で自動設定。任意の明示指定としても利用可能）、COMMON 設定 `mcp.enabled`（初期値 `true`）・`mcp.port`（初期値 `38281`、範囲 `1024`～`65535`）・`mcp.requestTimeoutSeconds`（初期値 `5`）を追加する。既存の設定名は変更しない |
| 設定の反映 | プロジェクトと接続設定の変更は、次回のゲーム起動で反映する。MCP の待ち受けは統合サーバーの起動・停止に合わせる。専用サーバーでは今回は起動しない |
| フォルダーの照合 | 実在する絶対パスとして正規化し、Windows の大文字・小文字と末尾の区切りを考慮して照合する。明示指定は Bridge 登録先との完全一致。空欄時はゲーム実行フォルダーを含む登録先が1つの場合だけ自動設定する。複数候補から近さで選ばず、途中に別の `.git` ディレクトリ・ファイルがある候補は除外する |
| 認証 | WebSocket・ゲーム MCP とも `Authorization: Bearer <token>`。トークンは暗号学的乱数で32バイト生成する。Bridge 用は起動ごとに更新し、MCP 用は保存して再利用する |
| ファイルの保護 | 保存先のアクセス権を OS の仕組みで現在の利用者に限定し、一時ファイルから置き換えて書き込み途中の内容を読ませない。保護できないときは理由を示して接続機能を開始しない。Bridge 終了時は自分の起動の接続情報だけを削除し、MCP 設定とトークンは残す |
| HTTP・WebSocket の検証 | 待ち受け先は `127.0.0.1` に限定する。`Host` は自分の待ち受け先に対応する localhost の値だけを受け付け、`Origin` 付きの要求と認証に失敗した要求は拒否する。Bridge に伝える MCP URL も `127.0.0.1` の HTTP と `/mcp` に限定する |
| 再接続と疎通確認 | Mod は失敗後に1・2・4・8・15秒と間隔を広げ、以後は最大15秒で再試行する。試行ごとに接続情報ファイルを読み直す。接続と初回の応答の待ちは10秒まで、接続中は20秒ごとに疎通を確認し、60秒応答がなければ切断して再接続する |
| Bridge の表示 | 対象modごとに、ゲーム未接続・接続中（ワールド未起動）・ゲーム情報取得可能・接続エラーとその理由を表示する。トークンは画面・ログ・進捗に表示しない |

Mod と Bridge の独自の通信は、バージョン `1` の JSON とする。

- Mod は `hello` で `protocolVersion`、ゲーム起動ごとの `gameInstanceId`、`projectRoot`、正規化したゲーム実行フォルダー `gameDirectory` を送る。Bridge は認証・バージョン・対象modと同時接続数を確認し、`welcome` で `protocolVersion` と `projectId` を返す。`projectRoot` が空なら `gameDirectory` を使って自動照合する。従来のクライアントの明示指定では `gameDirectory` は不要。拒否時は `error` で機械判定用の `code` と利用者向けの `message` を返して閉じる。
- Mod は接続成立時とワールドの起動・停止時に `game_state` を送り、`gameInstanceId`、ワールドと MCP の利用可否、エラーの理由、利用可能な場合の MCP の `url` と `headers` を伝える。Bridge はその接続に割り当てた対象modだけに適用する。
- ゲーム情報は通信のスレッドから直接取得せず、既存の `GameInformationService` を通してサーバースレッドに処理を渡す。5秒で取得できなければタイムアウトとする。
- `get_player_snapshot` の入力スキーマは、プロパティを持たず追加プロパティを認めないオブジェクトとする。出力は既存の `PlayerSnapshot` に合わせ、`playerId`・`playerName`・`dimension`・`position`（`x`・`y`・`z`・`yaw`・`pitch`）・`mainHand` と `offHand`（それぞれ `itemId`・`count`）を持つ JSON とする。構造化した結果と同じ内容の JSON テキストを返し、読み取り専用の注釈を付ける。
- 取得失敗はツールのエラーとして返す。トークンや内部の例外全文は含めず、プレイヤー未接続・サーバー停止・タイムアウトなどの理由を伝える。
- ゲーム MCP は独自の WebSocket バージョンとは別に、MCP の標準プロトコルに従う。対応バージョンは、採用する既存クライアントとの互換性を検証して仕様書に記録し、未対応のバージョンを黙って受け付けない。

AI への受け渡しと実装方式:

- ゲーム MCP の接続先は、Bridge が管理する MCP とは別の `potamaid_game` として、計画・タスク・相談の次の実行開始時に渡す。既存の相談・追加指示にも反映する。接続が変わっただけでは応答中の AI を中断しない。読み込み済みの Codex スレッドで接続設定を反映する部分も、今回の変更対象とする。
- worktree の AI にも読み取り専用のゲーム情報を渡すが、そのゲームは起動元フォルダーのコードで動いており、worktree の未反映の変更を検証するものではないことを指示に明記する。
- Mod 側は Java 21 の HTTP サーバーと WebSocket クライアント、既存の Gson を使う最小限の MCP 実装とし、新しい Mod 用依存ライブラリは追加しない。MCP 標準の要求・応答・バージョン・ツール呼び出しの互換性を検証する。
- Bridge の WebSocket サーバーには `ws` を実行時依存として追加する。バージョンは、すでにロックファイルにある `8.22.0` に固定し、型定義は対応する `@types/ws` を開発用に追加する。既存の依存関係のバージョンは上げない。

今回の検証と完了条件:

- Mod のビルド、ゲーム情報取得・MCP の要求とエラー・認証・ライフサイクルに適したテスト、Bridge のテスト・型チェック・lint、差分チェックを行う。Mod のビルドは `mod/` で `gradlew.bat build` を実行する。
- 実機では、Bridge の相談から現在地と手持ちを取得できること、既存の相談でも次の指示で使えること、Bridge なしでも既存の AI アプリから取得できること、Bridge の後起動・再起動で Mod が再接続すること、ワールドを閉じて開き直したときの MCP の接続を確認する。
- MCP の直接接続は Codex・Claude Code それぞれで確認し、検証できた環境・クライアントの版と未確認の範囲を記録する。実機確認のために `runClient`・`runServer` を起動するときは、改めて作者に確認する。
- 静的検証の成功と実機で確認できた内容を分けて報告し、実機で未確認の項目を完了扱いにしない。説明用 README は増やさず、この仕様書に利用手順をまとめる。

#### 対象modの初回設定の自動化（2026-11-01 追加）

利用者から「ここの設定も自動化したい」と追加依頼があったため、初回に TOML へパスを入力する方式を次のように変更した。

- `bridge.projectRoot` の初期値の空文字列を「自動設定」とする。Mod は Minecraft の実在するゲーム実行フォルダーを Bridge に伝える。
- Bridge は登録済みの対象modのうち、ゲーム実行フォルダーと同じか、その祖先であるフォルダーを照合する。候補が1つだけの場合に紐付ける。たとえば `PotamAId/mod/run` から起動し、`PotamAId/mod` だけを登録してあれば、自動でその対象modにつながる。
- 起動フォルダーから候補までの途中に `.git` ディレクトリまたはファイルがあれば、その候補は使わない。これにより、登録先の中に置かれた別のリポジトリや worktree を、外側の対象modに誤って紐付けない。その worktree 自体を登録している場合は、その登録先を利用できる。
- リポジトリルートとその子の Mod フォルダーを両方登録しているなど、候補が複数ある場合は自動で選ばない。候補なし・複数候補・フォルダーの確認失敗は、Mod のログと Bridge の未接続時の表示へ理由を出す。起動フォルダーがプロジェクト外にある通常のランチャー環境も、対応先を推測して接続しない。
- 従来の `bridge.projectRoot` に値がある場合は、その完全一致の指定を優先する。指定に失敗しても別の対象modへ自動で切り替えない。同じ対象modへの2つ目のゲームの拒否も維持する。
- ゲームの実行フォルダーは接続のたびに照合し、Bridge の後起動・再起動・対象modの登録後の再試行にも対応する。`bridge.projectRoot` の設定変更自体は Minecraft の再起動後に反映する。保存済みの手動指定は勝手に書き換えない。

#### 今回の実装の利用手順

1. Bridge に、開発する対象modのフォルダーを登録し、そのフォルダー配下の `run` などから Minecraft を起動する。通常は `potamaid-client.toml` を編集する必要はない。`bridge.enabled = true`、`bridge.projectRoot = ""` が初期値で、自動で照合する。
2. 過去に `bridge.projectRoot` を設定済みで自動設定へ切り替えたい場合は、値を空にして Minecraft を再起動する。自動照合できない場所から起動する場合や複数候補がある場合は、引き続き `projectRoot = '対象modの絶対パス'` で接続先を明示できる。Windows のパスは TOML の単一引用符で囲むと、バックスラッシュのエスケープが不要。指定時は Bridge に登録したフォルダーと一致させる。
3. `config/potamaid-common.toml` の `[mcp]` は、通常は `enabled = true`、`port = 38281`、`requestTimeoutSeconds = 5` のままでよい。同時に複数のゲームを起動する場合は、各ゲームに別のポートを設定する。設定を変えたら Minecraft を再起動する。
4. Bridge と Minecraft を起動する。起動の順序は問わない。Bridge のフッターは、選択中の対象modの「ゲーム未接続」「接続中（ワールド未起動）」「ゲーム情報取得可能」またはエラーの理由を表示する。
5. シングルプレイのワールドを開き、Bridge の相談で「現在地と両手に持っているものを、ゲームから取得して教えて」と尋ねる。既存の相談でも次の発言から使う。接続の変化だけでは応答中の AI を止めない。

開発環境の設定ファイルは `mod/run/config/` にできる。Bridge 接続を無効にしても、統合サーバーのゲーム MCP は独立して動く。ゲーム MCP の接続情報はワールドを開いたときに `<ユーザーホーム>/.potamaid/games/<識別値>/mcp.json` に作られる。識別値はゲーム実行ディレクトリ（この開発環境では `mod/run`）の実在パスを正規化した SHA-256。保存済みトークンを再利用し、ワールドを閉じても設定ファイルを残す。ポートの使用中・保存設定の破損・アクセス権の制限に失敗した場合は、ゲーム MCP を起動しない。

Windows のパスを二重引用符で囲んだ `projectRoot = "C:\Users\..."` は、バックスラッシュが TOML のエスケープとして解釈されるため使わない。`projectRoot = 'C:\Users\Owner\Documents\GitHub\PotamAId'` のように単一引用符で囲むか、`projectRoot = "C:/Users/Owner/Documents/GitHub/PotamAId"` のようにスラッシュを使う。設定の解析に失敗すると、NeoForge は `potamaid-client-1.toml.bak` などに元の内容を保存して初期値へ戻す。ゲーム起動中の保存も監視されるため、設定を編集するときは Minecraft を終了しておくと、編集中の内容が読み込まれるのを避けられる。変更の反映には再起動が必要。

Bridge を使わず CLI から接続する場合は、生成済みの `mcp.json` を読み、認証情報を表示せず環境変数で渡せる。以下は PowerShell の例。`<mcp.json の絶対パス>` を自分の生成済みファイルに置き換える。登録操作は各 CLI の利用者設定を変更するため、利用者自身が実行する。同名の `potamaid_game` がある場合は既存の設定を確認する。

```powershell
$gameMcp = Get-Content -Raw '<mcp.json の絶対パス>' | ConvertFrom-Json

# Codex CLI: このターミナルから起動したプロセスにだけトークンを渡す
$env:POTAMAID_GAME_MCP_TOKEN = $gameMcp.headers.Authorization.Substring(7)
codex mcp add potamaid_game --url $gameMcp.url --bearer-token-env-var POTAMAID_GAME_MCP_TOKEN
codex

# Claude Code: 設定には秘密そのものではなく環境変数の参照を保存する
$env:POTAMAID_GAME_MCP_AUTH = $gameMcp.headers.Authorization
$claudeGameMcp = @{
    type = 'http'
    url = $gameMcp.url
    headers = @{ Authorization = '${POTAMAID_GAME_MCP_AUTH}' }
} | ConvertTo-Json -Compress
claude mcp add-json --scope user potamaid_game $claudeGameMcp
claude mcp list
claude
```

次のターミナルから使うときも `mcp.json` を読み込んで環境変数を設定する。トークンをチャット・URL・コマンドのリテラル・Git 管理下の設定へコピーしない。ほかの CLI・IDE・デスクトップアプリへ設定する際も、HTTP の URL と Authorization ヘッダーを扱える設定を使う。各クライアントの手順は [Codex の設定リファレンス](https://learn.chatgpt.com/docs/config-file/config-reference)・[Claude Code の MCP 手順](https://code.claude.com/docs/en/mcp) を参照する。

#### 通信の実装と検証状況（2026-11-01）

- ゲーム MCP は、初期化を行う MCP `2025-03-26`・`2025-06-18`・`2025-11-25` に対応する。HTTP POST の JSON 応答を使い、サーバー側のセッション ID と SSE 配信は使わない（GET は 405）。未対応の版は初期化でエラー、未対応の `MCP-Protocol-Version` ヘッダーや要求ごとのプロトコルメタデータは HTTP 400 で拒否する。

### ゲーム内の相談と状態確認（2026-11-01 追加）

作者が承認した最小案として、同じ PC のシングルプレイで、クライアントのチャットコマンドから読み取り専用の相談と状態確認を提供する。チャットには途中経過を自動で流さない。将来の専用 GUI・設置ディスプレイでの途中経過表示は別の段階とし、通信・選択管理（Bridge の `ModControl`）、クライアントの接続、チャットへの描画を分けている。

#### 今回の操作と表示

- 相談の新規作成・一覧・選択・続きの送信・中止、目標とタスクの一覧・状態・履歴の確認を実装する。作成した相談は自動で選択する。Bridge で作成した既存の相談も選択できる。
- 新規相談は Bridge の既定の実行設定を使い、既存相談はその設定とセッションを引き継ぐ。読み取り専用の権限と実行枠は Bridge の既存処理を使う。ゲーム情報は必要時に既存のゲーム MCP で取得する。画像や座標等を指示に固定して添付する機能は今回は含めない。
- 選択中の相談の順番待ち・応答中・応答終了・失敗と、最後の回答をローカルチャットへ表示する。推論・途中の発言・ツール実行は自動表示せず、`history` で確認する。中止しても相談の履歴は残り、次の質問で同じ相談を続けられる。
- 接続中の対象modで目標が確認待ち／反映待ちになったとき、タスクが失敗したとき、承認待ちになったときは短く知らせる。承認の内容の確認と回答は [ゲーム内の承認操作](#ゲーム内の承認操作2026-11-03-決定) でも Bridge でも行える。通知は Bridge のウィンドウのフォーカスにかかわらずゲームへ送る。
- 目標の作成・編集指示は、この段階ではゲーム内操作に含めない。計画の承認・操作の承認回答・タスクの中止／再開と、承認への二重回答の同期は [ゲーム内の承認操作](#ゲーム内の承認操作2026-11-03-決定) で定義した。
- 操作はクライアントだけで受け付け、サーバーのチャットやパケットで指示を運ばない。選択や履歴はワールドのセーブへ保存しない。タイトル画面用の操作 UI は今回は追加しない。

#### コマンドと利用手順

Bridge と更新後の Minecraft を起動し、シングルプレイのワールドを開いて実行する。対象modの登録・自動照合は上記の連携手順と同じ。`/potamaid` 単体でコマンドの概要を表示する。既存の `/potamaid info` はゲーム情報の確認用として残る。

| コマンド | 内容 |
|---|---|
| `/potamaid status` | 接続中の対象mod名、目標・タスク・相談の件数、承認待ちの件数、選択中の相談 ID |
| `/potamaid consult new <質問>` | 読み取り専用の相談を作成して選択 |
| `/potamaid consult list [ページ]` | 相談の ID・題名・状態。1ページ5件 |
| `/potamaid consult select <ID>` | 相談を選択して直近5件の履歴を表示 |
| `/potamaid consult send <質問>` | 選択中の相談の続きを送信。応答中・順番待ちは送れない |
| `/potamaid consult cancel` | 選択中の相談の実行・順番待ちを中止 |
| `/potamaid consult history [before]` | 選択中の相談の直近5件、または指定した連番より前の5件 |
| `/potamaid goals [ページ]` | 目標の ID・題名・状態・計画の要約。1ページ5件 |
| `/potamaid goal <ID> [ページ]` | 目標と、そのタスクの状態・最新の途中経過・結果。タスクは1ページ5件 |
| `/potamaid task <ID>` | タスクの状態・説明・最新の途中経過・結果・失敗理由・再起動が必要か |
| `/potamaid goal <ID> history [before]` | 計画作成の履歴 |
| `/potamaid task <ID> history [before]` | タスクの履歴 |

ID は一覧の UUID 全体か、一意に決まる先頭8文字以上を使う。見つからない場合や複数候補がある場合は操作しない。ページは1から始める。履歴に前のページがあるときは `before` に指定する連番を表示する。たとえば `consult history 123` は連番123より前の履歴を取得する。

Minecraft のチャット入力の長さ制限があるため、長い指示は Bridge の画面から送る。通信上の質問は2000文字まで。一覧・履歴は5件ずつ、履歴と最後の回答の本文は各2000文字まで、目標の要約は1000文字まで、タスクの各説明・結果等は500文字まで表示し、それ以上は Bridge での確認を案内する。コマンドの出力・差分などの詳細データはゲームに配信しない。

#### 通信と再接続

- 接続用ファイルの `schemaVersion` は `1` のまま、独自 WebSocket の `protocolVersion` を `2` にする。`hello`・`welcome` も `2` を照合する。旧版は拒否し、認証・Host・Origin・対象modの自動照合・ゲーム MCP の通信と保存先は維持する。上記の初期実装仕様にある `protocolVersion: 1` は接続のみの段階の記録であり、現在は `2` を用いる。
- 操作は `{ type: "request", requestId, gameInstanceId, operation }`、結果は `{ type: "response", requestId, ok: true, data }` または `{ type: "response", requestId, ok: false, error }`。`requestId` は操作ごとの UUID。`operation.action` は `status`、`consult_list`、`consult_new`、`consult_select`、`consult_send`、`consult_cancel`、`goals`、`goal`、`task`、`history` に限定する。該当操作にだけ `id`・`text`・`page`・`owner`・`before` を付け、余分なフィールドと不正な値は拒否する。
- 接続時に確定した対象modにだけ操作・照会できる。要求で対象modを切り替えられない。対象の ID は必ず所属を検証する。通常の操作エラーは接続を維持して返し、接続・要求の形式が不正な場合は切断する。
- 選択中の相談の状態変化は `{ type: "consult_state", consult, answer }`、短い通知は `{ type: "notice", kind, title, body }` で送る。途中のストリーミングは送らない。状態・履歴のデータに接続設定や認証ヘッダーを含めず、送信前に既知の接続トークンを伏せる。自由文をクリック操作などの JSON コンポーネントとして解釈しない。
- 同じ接続内では直近128件の要求 ID の結果を保持し、同じ ID の要求に対して操作を再実行しない。再接続をまたぐ重複排除や操作の自動再送は行わない。Mod は15秒以内に結果を受け取れなかった場合や送信後に切断した場合、結果未確認として一覧・履歴・Bridge での確認を案内する。未接続時は操作を送らない。
- 再接続後は対象modの現在の件数・承認待ちを自動で取得する。相談の選択は接続ごとに解除する。`consult list` と `select` で既存相談を選び直せば直近履歴を取得できる。切断中の通知の自動再送、未確認の操作の自動再試行、ゲーム再起動後の選択復元は今回の対象外。ゲームを閉じても Bridge の AI を自動中止しない。

### ゲーム内の承認操作（2026-11-03 決定）

Bridge は中継用の補助アプリであり、ゲーム内からほとんどの機能に触れられるようにするのが作者の方針。その第一歩として、計画の承認・AI の操作の承認回答・タスクの中止／再開をゲーム内から行えるようにする。目標の作成・編集指示・計画の編集は引き続き Bridge の画面のみで、後の段階で対応する。

#### 決定事項

- **操作の出し方**: チャットのコマンド。承認の内容を出す専用 GUI は別の段階とする。
- **同じ承認への二重回答**: 先に届いた回答だけを有効にする。遅れた側には、先にどちらで回答したか（ゲーム内／Bridge の画面／中止による取り消し）を示して失敗を返す。承認が解決したら、Bridge はゲームへ `approval_resolved` を送り、Bridge の画面は既存の状態配信で同期する。回答の内容は `approval_resolved` に含めない。
- **回答できる範囲**:

| 承認の種類 | ゲーム内で行えること |
|---|---|
| コマンドの実行・ファイルの変更 | 許可（`allow`）、このセッションの間は許可（`always`）、拒否（`deny`） |
| AI からの質問 | 秘密の回答を含まない質問に、選択肢の番号か自由文で回答。拒否もできる |
| 秘密の回答を含む質問 | 拒否のみ。回答は Bridge の画面で行う（チャットの履歴・ログに秘密を残さないため） |
| MCP の入力フォーム・URL を開く要求 | 拒否のみ。回答は Bridge の画面で行う |

- 計画の承認は、「計画の確認待ち」の目標だけ受け付ける。内容はこれまでの `goal <ID>` で確認し、タスクの編集は Bridge の画面で行う。
- 操作はクライアントだけで受け付ける。承認の ID は対象modの範囲で照合し、別の対象modの目標・タスク・承認には操作できない。
- `protocolVersion` は `2` のまま。既存のメッセージの形は変えず、操作とメッセージの種類を追加しただけのため。旧版の Bridge に新しい Mod を接続した場合、新しい操作は「操作に失敗しました」と返るが、接続は続く。

#### コマンド

| コマンド | 内容 |
|---|---|
| `/potamaid approvals [ページ]` | 承認待ちの一覧。ID・誰が求めているか・内容・回答のコマンド。1ページ5件 |
| `/potamaid approval <ID> allow|always|deny` | コマンド・ファイル変更の承認に回答（`always` はこのセッションの間は許可） |
| `/potamaid approval <ID> answer <質問番号> <回答>` | 質問に回答。選択肢のある質問は番号（1から）で答える。自由な回答が許されている質問では、選択肢の範囲外の数字（ポート番号など）や文をそのまま回答にする。許されていない質問では範囲外の番号を拒否する。質問が複数あるときは1問ずつ答え、全部答えると送る |
| `/potamaid goal <ID> approve` | 「計画の確認待ち」の目標の計画を承認 |
| `/potamaid task <ID> cancel|resume` | タスクの中止・再開（Bridge の画面と同じ動作） |

承認の通知（`notice`）には `/potamaid approvals` での確認を案内する。ID の指定は先頭8文字以上で、既存の操作と同じ。

#### 通信

- `request` の `operation.action` に `approvals`（`page`）、`approval_respond`（`id`・`decision`: `allow`/`allowForSession`/`deny`）、`approval_answer`（`id`・`question`: 1〜20・`value`: 500文字まで）、`goal_approve`（`id`）、`task_cancel`（`id`）、`task_resume`（`id`）を追加した。余分なフィールドと不正な値は拒否する。
- 結果は `{ kind: "approvals", items, page, hasMore }`、`{ kind: "approval_progress", remaining: [未回答の質問番号] }`、`{ kind: "accepted" }`。
- Bridge から Mod へ `{ type: "approval_resolved", id, by: "app"|"game"|"cancel", decision }` を、その対象modの接続へ送る。Mod は `by` が `app`／`cancel` のときだけ表示する（`game` は自分の回答の結果で表示済み）。
- 質問への回答の途中経過は、Bridge が承認ごとに接続中だけ持ち、保存しない。承認が解決する、または接続が切れると破棄する。秘密の質問への回答は受け付けないため、途中経過にも通信にも載らない。
- 回答済みの承認への操作は、直近64件の解決済みの承認から「先にゲーム内で回答済み」「先に Bridge の画面で回答済み」「中止により取り消されています」を返す。ゲームへ返すエラーの文面は、固定の文だけにする。

#### 手動での確認

1. 編集タスクが承認を求める状況（`gradlew` の実行など）にし、ゲームに承認の通知が出ることと、`/potamaid approvals` に内容と ID が出ることを確認する。
2. `/potamaid approval <ID> allow` で AI が続きを実行し、Bridge の画面から承認が消えることを確認する。
3. 別の承認で、Bridge の画面で先に回答してから、ゲーム内で同じ承認に回答する。ゲームに「Bridge の画面で回答済み」と出て、AI へ二重に回答されないことを確認する。逆の順（ゲーム内が先）では、Bridge の画面にも「先にゲーム内で回答済み」と出ることを確認する。
4. AI の質問を出させ、`approval <ID> answer` で番号と自由文を答える。複数の質問では、途中で `approval_progress` の案内が出て、すべて答えると AI へ届くことを確認する。秘密の質問では回答を受け付けず、拒否だけできることを確認する。
5. 「計画の確認待ち」の目標で `/potamaid goal <ID> approve` を実行し、Bridge で実行が始まることを確認する。承認済みの目標に実行すると失敗することも確認する。
6. 実行中のタスクに `/potamaid task <ID> cancel`、その後 `resume` を実行し、Bridge の画面と同じ状態になることを確認する。
7. Bridge を終了して再起動すると、承認待ちが消える（保存しない）ことを確認する。

Minecraft の起動・停止を伴う操作は作者が手動で行う。
