# Bridge の Codex 実行と失敗時の扱い

この文書は、Bridge の実装上の保護と制約を説明します。実際の Codex への接続や、ゲーム内での動作確認とは別に、偽 app-server と偽プロバイダーで検証しています。

## タイムアウトと停止確認

- ターンの無応答時間が設定値を超えると、`turn/interrupt` を送り、同じスレッド ID・ターン ID の `turn/completed` を待ちます。停止要求への応答だけでは、対象modの次の編集タスクを実行しません。
- 停止完了を待つ時間には「要求の応答を待つ秒数」の設定を使います。期限内に停止を確認できない場合は失敗とし、その Bridge が持つ Codex プロバイダー全体で後続の実行を拒否します。新しいセッションの作成、既存セッションの再開、設定変更によるプロセスの起動し直しでも、この拒否を解除しません。
- `turn/start` の応答が失われた場合も、サーバー側では開始済みかもしれません。開始通知でターン ID が分かれば停止を要求し、分からない場合も期限付きで確認を待ちます。確認できなければ、同じく後続の実行を拒否します。
- この失敗は Codex の停止を保証するものではありません。実行中の Codex を停止したことと変更内容を確かめてから Bridge を再起動し、必要なタスクをやり直してください。ファイルの変更は自動では戻しません。

## 通知と承認の振り分け

- 発言・アイテム・エラー・完了通知と、承認・質問・MCP 入力要求は、スレッド ID とターン ID の両方で照合します。旧ターンの遅れた要求や回答は、新ターンに渡しません。
- MCP 入力要求の `turnId: null` は正式なプロトコルの値ですが、Bridge では対象ターンを安全に特定できません。旧ターンの遅延要求を現在のタスクや相談に表示しないため、この要求には `cancel` を返し、理由を Bridge のログに残します。ターンと関連付けられない MCP 入力要求には回答できない制約があります。

## 追加指示の保持

- 追加指示は、送信対象の ID を読み取っても SQLite から削除しません。`turn/start` の応答か `turn/started` で入力の受け付けを確認した時点で、その送信対象だけ削除し、ユーザーの指示として履歴に記録します。
- セッション開始・再開の失敗、開始前の中止、受け付けを確認できなかった送信では、指示を保持します。実行中に追加された別の指示も次のターンまで保持します。
- 未送信の指示が残った失敗タスクを自動で繰り返しません。「やり直す」か、新しい追加指示の送信で再開します。受け付け済みの指示は通常の追加ターンに重複送信しません。
- 応答喪失時は、指示を保持していても未実行と断定できません。停止を確認できないときの実行拒否と組み合わせ、利用者が状況を確認するまで自動で再送しません。
